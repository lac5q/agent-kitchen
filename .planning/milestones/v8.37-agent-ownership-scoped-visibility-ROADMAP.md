# Roadmap: Memroos v8.37 — Agent Ownership + Scoped Visibility

*Created: 2026-08-02*

## Status

Planned. Not started. Triggered by a live finding: a **reviewer** signed in and saw **every
agent in the fleet**.

This concretises v8.35 Phases 209 and 210 (P1/P2) with measured facts rather than plan-time
assumptions. v8.35 remains the statement of principle; this is the executable slice.

## The defect, measured (2026-08-02)

```
apps/memroos/src/app/api/agents/route.ts   no authenticateUser, no requireRole, no owner filter
registered_agents                          owner_user_id: 0 occurrences — no ownership column
proxy.ts                                   /api/* requires only `reviewer`
```

So any authenticated user — including the lowest role — lists all **59** agents. There is no
ownership concept to filter on, which is why this is not a one-line fix.

## What already exists (and changes the design)

| Fact | Consequence |
|---|---|
| **240 of 260** `space_members` rows are agents, across **4** spaces | A scoping primitive already exists **and is populated**. Do not invent a second one. |
| **0 agents are outside a space** | Space-based scoping works on day one with no coverage gap. |
| 20 human space memberships | Humans and agents already share the membership table (`member_type`). |
| Only **3 non-test routes** read `registered_agents` | Small blast radius. |
| `listRegisteredAgents()` / `getRegisteredAgent()` | Two natural chokepoints — filter there, not in each route. |

## The core design decision

**Visibility is scope, not rank.** These are two orthogonal axes and the current bug comes
from having only one:

- **Rank** (`ROLE_RANK`: reviewer 1 < operator 2 < admin 3) answers *what may I do* — register
  an agent, revoke a key, change policy.
- **Scope** (ownership + space membership) answers *which agents am I talking about*.

Because `ROLE_RANK` is linear, it is tempting to say "operator sees more than reviewer." That
is the trap: it makes visibility a function of seniority, so every new operator silently gains
sight of every agent. An operator should see the agents **in their spaces**, not all agents,
and a second operator in a different space should see a different set.

### The rule

```
visible(user) =
      agents owned by user
    ∪ agents in spaces where user is a member
    ∪ (all agents, if user is admin)
```

Unowned agents are visible to **admin only**, and surfaced as a defect to be claimed — which
is P1 ("no owner is a defect, not a default") made operational without breaking the fleet.

**Answering the operator's question directly:** no, an operator or reviewer should not see
other people's agents by default. They see their own plus their spaces'. Admin sees all,
because fleet administration is that role's purpose.

## Phase 220: Ownership column + backfill

**Requirements:** AGENTOWN-01..05

1. `registered_agents.owner_user_id TEXT REFERENCES users(id) ON DELETE CASCADE`, indexed.
   FK enforcement is already on (v8.35 Phase 206), so this cascade is real — deleting a user
   removes their agents, and `agent_api_keys` already cascades from there.
2. `ownerUserId` carried through `RegisterAgentInput` and the onboarding token, required for
   new registrations.
3. **Backfill for the 59 existing agents.** There is no record of who registered them, so
   inventing an owner would be a lie. They stay `NULL` and become **admin-visible only**,
   listed as unowned so they can be claimed deliberately. Recommend a short claim window,
   then treat still-unowned agents as candidates for deregistration.
4. Audit records `subject_user_id` **and** `actor_agent_id` (v8.32 P1's dual trail).
5. `RegisteredAgent.role` stays a free-text description and is **never** an authorization
   input — the RBAC role comes from the owning user.

## Phase 221: Scoped visibility at the chokepoint

**Requirements:** AGENTVIS-01..06

1. `listRegisteredAgents()` and `getRegisteredAgent()` take a **required viewer principal**.
   Making it required rather than optional is the point: a new call site cannot forget to
   scope and silently leak the fleet, which is exactly how the current defect exists.
2. The rule above, implemented **once**, in `agent-registry.ts`. Routes do not filter.
3. `/api/agents` and `/api/agents/[id]` authenticate and pass the viewer.
   `getRegisteredAgent` returns null for an out-of-scope agent — **404, not 403**, so the
   response does not confirm that an agent with that id exists.
4. `/api/security/capabilities` scoped the same way; it enumerates agents too.
5. Tests: a reviewer sees only their own + space agents; two operators in different spaces see
   disjoint sets; admin sees all; unowned are admin-only.
6. A regression test asserting **an unscoped call does not compile / throws** — the guard that
   keeps this from silently regressing.

## Phase 222: Enforce on the write paths

**Requirements:** AGENTVIS-07..09

Read scoping is worthless if any user can mutate any agent.

1. Heartbeat, deregister, key issuance, and capability edits all check the same scope.
2. `/api/agents/register` — currently loopback-authorised via `authorizeRegistryWrite`, which
   returns **true for any loopback request with no credential** — must record an owner. This
   is the token-free bypass v8.35 Phase 208 flagged; ownership makes closing it unavoidable.
3. An agent may never widen its own scope: `owner_user_id` is not client-settable on
   heartbeat or update.

## Phase 223: Ownership UI

**Requirements:** AGENTUI-01..04

1. Owner column on `/agents`, and the viewer's own agents distinguished.
2. Unowned agents shown as a **defect state**, not an empty cell — with a claim action.
3. Reassign ownership (admin), which is also the offboarding path: reassign, then disable.
4. The Team page's user row links to that person's agents, so "what does Eric still have"
   is one click.

## Open decisions for the operator

| # | Decision | Recommendation |
|---|---|---|
| D1 | Should operator see all agents? | **No** — their spaces only. Rank governs actions, scope governs visibility. |
| D2 | The 59 unowned agents | Admin-only until claimed; do not invent owners |
| D3 | Space membership as visibility, or ownership only? | **Both** — space membership is already populated and is how teams share |
| D4 | Out-of-scope agent by id | **404**, not 403 — do not confirm existence |
| D5 | Claim window before unowned agents are deregistered | Operator's call |

## Why this ordering

209 is the reported bug and is tempting to do first — but scoping without ownership can only
use space membership, which would leave every agent visible to every member of its space with
no accountable human. 208 first means the fix lands complete rather than being revisited.

## Relationship to v8.35

This delivers v8.35's **P1** (every agent has a responsible human) and the visibility half of
**P2** (an agent's reach is bounded by its owner). It does **not** deliver P3 (clearance
granted per-agent, never inherited) or the `ROLE_RANK`→capability migration — those remain
v8.35 Phase 210 and are still not started.
