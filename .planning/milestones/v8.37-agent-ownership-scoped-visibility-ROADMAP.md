# Roadmap: Memroos v8.37 — Agent Ownership + Scoped Visibility

*Created: 2026-08-02*

## Status

Planned. Not started. Triggered by a live finding: a **reviewer** signed in and saw **every
agent in the fleet**.

This concretises v8.35 Phases 209 and 210 (P1/P2) with measured facts rather than plan-time
assumptions. v8.35 remains the statement of principle; this is the executable slice.

## The defect, measured (2026-08-02)

```
apps/memroos/src/app/api/agents/route.ts   no authenticateUser, no requireRole, no owner filter
registered_agents                          owner_user_id: 0 occurrences — no ownership column
proxy.ts                                   /api/* requires only `reviewer`
```

So any authenticated user — including the lowest role — lists all **59** agents. There is no
ownership concept to filter on, which is why this is not a one-line fix.

## What already exists (and changes the design)

| Fact | Consequence |
|---|---|
| **240 of 260** `space_members` rows are agents, across **4** spaces | A scoping primitive already exists **and is populated**. Do not invent a second one. |
| **0 agents are outside a space** | Space-based scoping works on day one with no coverage gap. |
| 20 human space memberships | Humans and agents already share the membership table (`member_type`). |
| Only **3 non-test routes** read `registered_agents` | Small blast radius. |
| `listRegisteredAgents()` / `getRegisteredAgent()` | Two natural chokepoints — filter there, not in each route. |

## The core design decision

**Visibility is scope, not rank.** These are two orthogonal axes and the current bug comes
from having only one:

- **Rank** (`ROLE_RANK`: reviewer 1 < operator 2 < admin 3) answers *what may I do* — register
  an agent, revoke a key, change policy.
- **Scope** (ownership + space membership) answers *which agents am I talking about*.

Because `ROLE_RANK` is linear, it is tempting to say "operator sees more than reviewer." That
is the trap: it makes visibility a function of seniority, so every new operator silently gains
sight of every agent. An operator should see the agents **in their spaces**, not all agents,
and a second operator in a different space should see a different set.

### The rule

```
visible(user) =
      agents owned by user
    ∪ agents in spaces where user is a member
    ∪ (all agents, if user is admin)
```

Unowned agents are visible to **admin only**, and surfaced as a defect to be claimed — which
is P1 ("no owner is a defect, not a default") made operational without breaking the fleet.

**Answering the operator's question directly:** no, an operator or reviewer should not see
other people's agents by default. They see their own plus their spaces'. Admin sees all,
because fleet administration is that role's purpose.

## Phase 220: Ownership column + backfill

**Requirements:** AGENTOWN-01..05

1. `registered_agents.owner_user_id TEXT REFERENCES users(id) ON DELETE CASCADE`, indexed.
   FK enforcement is already on (v8.35 Phase 206), so this cascade is real — deleting a user
   removes their agents, and `agent_api_keys` already cascades from there.
2. `ownerUserId` carried through `RegisterAgentInput` and the onboarding token, required for
   new registrations.
3. **Backfill for the 59 existing agents.** There is no record of who registered them, so
   inventing an owner would be a lie. They stay `NULL` and become **admin-visible only**,
   listed as unowned so they can be claimed deliberately. Recommend a short claim window,
   then treat still-unowned agents as candidates for deregistration.
4. Audit records `subject_user_id` **and** `actor_agent_id` (v8.32 P1's dual trail).
5. `RegisteredAgent.role` stays a free-text description and is **never** an authorization
   input — the RBAC role comes from the owning user.

## Phase 221: Scoped visibility at the chokepoint

**Requirements:** AGENTVIS-01..06

1. `listRegisteredAgents()` and `getRegisteredAgent()` take a **required viewer principal**.
   Making it required rather than optional is the point: a new call site cannot forget to
   scope and silently leak the fleet, which is exactly how the current defect exists.
2. The rule above, implemented **once**, in `agent-registry.ts`. Routes do not filter.
3. `/api/agents` and `/api/agents/[id]` authenticate and pass the viewer.
   `getRegisteredAgent` returns null for an out-of-scope agent — **404, not 403**, so the
   response does not confirm that an agent with that id exists.
4. `/api/security/capabilities` scoped the same way; it enumerates agents too.
5. Tests: a reviewer sees only their own + space agents; two operators in different spaces see
   disjoint sets; admin sees all; unowned are admin-only.
6. A regression test asserting **an unscoped call does not compile / throws** — the guard that
   keeps this from silently regressing.

## Phase 222: Enforce on the write paths

**Requirements:** AGENTVIS-07..09

Read scoping is worthless if any user can mutate any agent.

1. Heartbeat, deregister, key issuance, and capability edits all check the same scope.
2. `/api/agents/register` — currently loopback-authorised via `authorizeRegistryWrite`, which
   returns **true for any loopback request with no credential** — must record an owner. This
   is the token-free bypass v8.35 Phase 208 flagged; ownership makes closing it unavoidable.
3. An agent may never widen its own scope: `owner_user_id` is not client-settable on
   heartbeat or update.

## Phase 223: Ownership UI

**Requirements:** AGENTUI-01..04

1. Owner column on `/agents`, and the viewer's own agents distinguished.
2. Unowned agents shown as a **defect state**, not an empty cell — with a claim action.
3. Reassign ownership (admin), which is also the offboarding path: reassign, then disable.
4. The Team page's user row links to that person's agents, so "what does Eric still have"
   is one click.

## Phase 224: Optional directory sync (supported, never required)

**Requirements:** AGENTDIR-01..04

Operator constraint, stated 2026-08-02: *"build to support it but not require it."*
Ownership and teams must work fully with nothing connected; a directory is an accelerator
for populating them, never a dependency.

This follows the pattern the codebase already uses twice — `getGoogleOidcConfig()` and
`getEmailConfig()` both return `null` when unconfigured, and the UI hides the feature rather
than breaking. `/api/auth/capabilities` already reports that posture so an admin can tell
"not set up here" from "not working".

1. Teams are manually managed by default. Directory sync, when configured, **populates**
   membership; it never becomes the only way to create a team.
2. Sync maps a directory group to a MemroOS space. Membership is refreshed on sign-in and on
   demand — not a background job that silently drifts.
3. **Ownership is never sourced from the directory.** "This agent belongs to Eric" is a
   MemroOS fact that no external system knows. Only *people and teams* sync.
4. Multi-domain by construction: `epiloguecapital.com` and `cordant.ai` are **separate
   Workspaces under different control**. The operator administers Epilogue's directly and
   expects delegated access to Cordant's. Neither may be assumed present, and one being
   connected must not imply the other.

**Not scheduled.** Worth doing when headcount makes manual membership annoying — with three
people it is not. Recorded so the ownership model is designed to accept it later without
rework.

## Phase 225: Agent surface UX review — legibility, layout defects, responsiveness

**Requirements:** AGENTUX-01..06

Raised by the operator on 2026-08-02 from a live screenshot of `/agents`: capability badges
were painting on top of the Edit button, and *"I still can't tell what agents belong to what
users."* Ownership is now enforced correctly in the API; this phase is about it being
**legible**, and about the surface not having visual defects.

### Measured root causes (2026-08-02)

| Defect | Cause |
|---|---|
| Overlapping text | `agent-registry-table.tsx` used bare `fr` tracks. A bare fraction may shrink below its content's width, and the content then paints over the next column. Capability names are unbounded (`Write Episodic Memory`), so they overflowed into Action. |
| Owner column uninformative | Rendered `"You"` whenever the viewer owned the row. After the backfill assigned all 59 oracle-1 agents to one admin, **every row read "You"** — correct, and useless for seeing distribution. |
| Not responsive | The file was one of only **2 of 14** components with a hardcoded `grid-cols-[…]` and **zero** `sm:`/`md:`/`lg:` breakpoints. A 9-column grid has no usable narrow-width form. |

*Partially addressed already:* `minmax()` floors replaced the bare `fr` tracks, the owner's
name is now always shown with `(you)` as a secondary marker, and the table collapses to a
labelled card layout below `lg`. The remaining criteria are the ones that need design input
rather than a bug fix.

1. **Owner is filterable and groupable.** A filter chip row for owner, matching the existing
   PROTOCOL / STATUS / LIVENESS rows. With one owner and 59 agents a column cannot answer
   "who has what" — a filter and a count can.
2. **Unowned is actionable, not just flagged.** Phase 223 criterion 2 asked for a **claim
   action**; today the amber "Unowned" badge is inert. Claim must be one click for an admin.
3. **A person links to their agents.** Phase 223 criterion 4, still unbuilt: the Team page's
   user row needs a link to that person's agents, so *"what does Eric still have"* is one
   click. This is also the offboarding path.
4. **Audit the other 13 components** carrying a hardcoded `grid-cols-[…]`. Same `minmax()`
   floor rule; same overlap risk. `agent-security-modes-panel.tsx` (3 fixed / 1 responsive)
   and `ui/card.tsx` (1 fixed / 0 responsive) are the next-worst.
5. **A viewport regression test.** Render the agents table at 375 / 768 / 1280 and assert no
   horizontal body overflow and no overlapping bounding boxes. Without this the defect
   returns the next time a column is added — it was added by a previous phase, not by
   original design.
6. **Consistency pass across the operator console.** Column ordering, empty-vs-defect state
   styling, and truncation behaviour should read as one system. Scope this after 1–5; it is
   the only criterion here that is taste rather than defect.

**Ordering:** 1–3 are user-visible gaps in the ownership story and belong with v8.37. 4–6 are
app-wide and can run independently of the ownership work.

## Phase 226: View-as — an admin sees the console as another user sees it

**Requirements:** VIEWAS-01..07

Operator request, 2026-08-02: *"I need to be able to login as admin into the memroos platform
as any user to see what they can view."*

Scoped visibility (Phases 220–222) made "what can this person actually see?" a real question
with a non-obvious answer, and today the only way to answer it is to hold that person's
credentials. That is the wrong tool: it is unauditable, it needs their password, and it
cannot be revoked. View-as answers the same question without ever becoming that user.

This is the single feature in the milestone most likely to be built into a privilege
escalation, so the constraints are part of the requirement, not polish.

1. **Read-only, enforced server-side.** A view-as session may not write, mutate, deregister,
   rotate a key, change a role, or send. The block belongs at the same chokepoint as
   `listAgentsVisibleTo` — not in the UI, and not by hiding buttons.
2. **Admin-only to start, and it never elevates.** The effective permission set is the
   *intersection* of the admin's and the target's, never the union. Viewing as an admin from
   another tenant must not grant that tenant's reach.
3. **The session says whose eyes it is.** A distinct session claim (`viewingAs`), not a
   swapped `userId` — the acting human stays the admin in every audit record. v8.32's dual
   trail already wants `subject_user_id` **and** actor; this is the same shape.
4. **Audited on entry and exit**, with the target named. "Who looked at Eric's data, and
   when" must be answerable. A silent impersonation is worse than no feature.
5. **Unmistakable in the UI.** A persistent banner naming the target and a one-click exit.
   The failure mode to design against is an admin forgetting they are in view-as and
   reporting what they saw as their own view.
6. **Time-boxed.** It expires on its own (~15 min) rather than living as long as the session.
7. **Tests:** a view-as session sees exactly `listAgentsVisibleTo(target)`; every write verb
   is refused; the audit row names both humans; expiry ends it; and viewing as a *higher*
   role than the admin grants nothing extra.

**Not started.** Depends on Phase 221's chokepoint, which is the thing that makes it
implementable in one place rather than sprayed across routes.

## Phase 227: Per-user tool connections

**Requirements:** TOOLOWN-01..07

Raised 2026-08-03 while fixing revoke. Tool connections (Circleback, Notion, Gmail,
Calendar, Drive, Linear) are **instance-wide**: `listVaultConnections()` and
`deleteVaultConnection(providerKey)` take no user id, and Nango connections are not scoped
either. On Cordant that means one Circleback serves everyone on the host, the card's
"as luis@epiloguecapital.com" is merely whoever authorised it, and **any user can revoke it
for all of them**.

This is the same defect as agent visibility, one layer up — and it lands before Cordant
employees onboard, or the first thing Eric does is silently repoint the operator's
integrations.

### Measured today (2026-08-03, cordant-hermes-01)

| | |
|---|---|
| Nango connections | 8, none carrying a user dimension |
| `circleback-mcp` rows | **2** — residue of a failed revoke, invisible in the UI, which shows one card |
| Vault schema | keyed on `provider_key`, so it cannot represent two owners of one provider |

### The design decision

Reuse the shape Phases 220–222 already proved rather than inventing a second one:
`owner_id` plus an explicit shared flag, enforced at one chokepoint. Ownership answers
"whose credential is this", the flag answers "who may use it".

The distinction matters more here than for agents, because both cases are legitimate and
common: a company Notion workspace **should** be org-wide, while a personal Gmail **must
not** be. Today the model cannot express either, because it has no owner at all.

1. **`tool_connections.owner_id`**, FK to `users(id)` `ON DELETE SET NULL` — matching
   `registered_agents`. Losing a person must orphan their connections, never destroy the
   record of what they authorised.
2. **`is_shared`**, default 0. A shared connection is usable by everyone but manageable
   only by its owner or an admin — the exact `canViewAgent` / `canManageAgent` split.
3. **Nango `connection_id` carries the user**, so two people can hold the same provider
   concurrently. This is the piece that makes "Eric's Circleback" and "Luis's Circleback"
   coexist rather than overwrite.
4. **One chokepoint**, `listToolConnectionsVisibleTo(viewer)`, mirroring
   `listAgentsVisibleTo`. Routes do not filter. `/api/tools/connections`,
   `/api/tools/disconnect`, and every credential fetch go through it.
5. **Revoke is owner-or-admin.** Right now any signed-in user can revoke a connection they
   did not create and do not own.
6. **Migration must not orphan what exists.** The 8 live connections predate ownership;
   they become admin-owned and `is_shared = 1`, preserving today's behaviour exactly, and
   are listed as needing an owner. Silently making them private would break every agent
   mid-flight.
7. **Tests:** two users hold the same provider without collision; a non-owner cannot revoke;
   a shared connection is usable but not manageable by a non-owner; deleting a user orphans
   rather than deletes; and the duplicate-row case above is reported rather than hidden.

**Not started.** Depends on Phase 221's chokepoint. Sequence it before Cordant employee
onboarding, not after.

## Open decisions for the operator

| # | Decision | Recommendation |
|---|---|---|
| D1 | Should operator see all agents? | **No** — their spaces only. Rank governs actions, scope governs visibility. |
| D2 | The 59 unowned agents | Admin-only until claimed; do not invent owners |
| D3 | Space membership as visibility, or ownership only? | **Both** — space membership is already populated and is how teams share |
| D4 | Out-of-scope agent by id | **404**, not 403 — do not confirm existence |
| D5 | Claim window before unowned agents are deregistered | Operator's call |
| D6 | Directory sync | **Support, never require** (Phase 224). Ownership must work with nothing connected. |

## Why this ordering

209 is the reported bug and is tempting to do first — but scoping without ownership can only
use space membership, which would leave every agent visible to every member of its space with
no accountable human. 208 first means the fix lands complete rather than being revisited.

## Relationship to v8.35

This delivers v8.35's **P1** (every agent has a responsible human) and the visibility half of
**P2** (an agent's reach is bounded by its owner). It does **not** deliver P3 (clearance
granted per-agent, never inherited) or the `ROLE_RANK`→capability migration — those remain
v8.35 Phase 210 and are still not started.
