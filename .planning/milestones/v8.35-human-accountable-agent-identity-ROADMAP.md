## Governing principles (operator-stated; every phase is judged against these)

**P1 — Every agent has a human responsible.**
No owner is a defect, not a default. Unowned agents fail closed and are visible as a
problem state.

**P2 — An agent's access is always a subset of its owner's.**
An agent narrows, never widens. Enforced by construction — an intersection in code — not by
policy documentation.

**P3 — Clearance is granted to an agent, never inherited.**
Eric cleared for Confidential does **not** make his Claude Code Confidential. Agents read
untrusted text — documents, web pages, emails — and are prompt-injectable. If a planted
instruction lands in an agent carrying its owner's full clearance, the injection inherits
CEO reach. Eric loses nothing: he reads confidential material himself, in the browser. His
agent is simply not a standing key to the vault.

P3 follows from P2 and is where the security payoff lands.

### The one-line statement of the whole milestone

> Today the agent declares its own identity and clearance via `MEMROOS_AGENT_ID` /
> `MEMROOS_AGENT_ROLE` on the laptop. After this, the **server decides**, from the
> credential.

The current default (`"agent"`, which cannot read restricted or confidential docs) fails
safe *in spirit* — but anyone who can edit an environment variable raises their own
clearance. The protection is real and unenforceable.

## Sizing finding: Phase 210 is a BUILD, not a rewire

> **Correction (2026-07-31, adversarial review).** An earlier draft of this roadmap claimed
> the v8.2 Policy Plane already evaluates capabilities and that Phase 210 was therefore a
> cheap rewire. **That was wrong**, and it under-priced the largest phase in the milestone.
> The citations were individually correct; the inference from them was not. Corrected below.

**What actually exists.** The "capability" policy domain is narrow, hardcoded, and fails open:

- `security-policy.ts:12-26` — `DISPATCH_CAPABILITIES` and `A2A_SEND_CAPABILITIES` are
  **literal string `Set`s**, not data-driven grants.
- **There is no generic `hasCapability(principal, capability)` anywhere in the tree** —
  verified, zero hits.
- `security-policy.ts:36-42` — `allowLegacyWhenUndeclared()` returns **true for any agent
  with zero declared capabilities** when `NODE_ENV !== "production"` and the profile is
  `local-dev`, or whenever `MEMROOS_ALLOW_LEGACY_UNDECLARED_CAPABILITIES` is set.
  **A plane that defaults to allow-on-empty cannot carry P2 or P3.**
- The engine's two production consumers (`lib/gsd/adapter-policy-gate.ts:93`,
  `api/policy/knowledge/route.ts:5`) sit on neither the 58 `authenticateAgentHeaders` routes
  nor the knowledge read path.
- `engine.ts:8-12` — the **knowledge** domain, the one that governs clearance, is a
  declarative pass-through; the real check lives in the Python knowledge MCP
  (`services/knowledge-mcp/knowledge_system/mcp_server.py`, ~line 587). The engine never
  touches it.

**Worse: `agent_capabilities` is a self-declaration store, not a grant store.** Capabilities
are client-writable today:

- `api/agents/register/route.ts:52-53` accepts caller-supplied `capabilities` verbatim,
  gated only by `authorizeRegistryWrite` (`:69`) — which returns **true for any loopback
  request with no credential** (`operator-auth.ts:35-37`).
- `api/onboarding/register/route.ts:67` falls back to `parsed.input.capabilities` when the
  invite did not specify them.
- Both reach `replaceCapabilities(input.id, input.capabilities)` (`agent-registry.ts:325`).

An agent declaring its own capabilities is the same defect class as an agent declaring its
own `MEMROOS_AGENT_ROLE`. **Making grants server-authoritative is in scope for this
milestone**, not assumed.

**Consequences for the plan:**

1. Phase 210 is **greenfield authorization work**, priced accordingly — split into 203a
   (human capability model) and 203b (intersection + clearance).
2. **`ROLE_RANK` retirement has a blast radius of 94** `requireRole`/`ROLE_RANK` references
   outside tests — including `proxy.ts:202,210,216`, which gates admin/operator/reviewer
   independently. It needs a CI gate and a migration plan of the same rigour Phase 211 gives
   its 58 call sites. Running two authorization models at once is how confused-deputy bugs
   happen.
3. **Do not attempt to validate this via shadow mode.** `policy/shadow.ts:1-13` replays
   recorded decisions against a proposed manifest's *dimension rules*; it cannot compare
   `ROLE_RANK` against a capability model. An earlier draft instructed the implementer to
   confirm something impossible.

## Phase 213: Revocation Integrity

**Goal:** Make revocation and cascade real. Every `ON DELETE CASCADE` in the schema is
currently decorative.

**Requirements:** HAIA-01..04

**Why:** `db.ts:25-27` sets `journal_mode`, `synchronous`, `busy_timeout` — and **never sets
`foreign_keys`**. SQLite defaults it OFF. Adding `owner_user_id ... ON DELETE CASCADE` in
Phase 209 would ship a documented guarantee that does nothing.

**Success Criteria:**
1. `PRAGMA foreign_keys = ON` in `db.ts`, with a test asserting it on a fresh connection.
2. `PRAGMA foreign_key_check` clean before enforcement. **Known work: 56 rows on oracle-1.**
   Decide repair-vs-delete per relationship and record each decision. cordant needs none.
3. Enforcement may land on cordant-hermes-01 **first** — already clean, and it is Eric's host.
4. `agent_api_keys` gains `expires_at`; issuance sets a default TTL; expired keys fail auth.
   **Existing-key triage is empty** — zero keys exist.
5. `users` gains a disable/soft-delete column, so "offboard Eric" has an implementable
   trigger that is not a hard delete. Required for the P1 offboarding story.
6. The three table-rebuild migrations toggle `PRAGMA foreign_keys` OFF/ON around themselves
   (`db-schema.ts:811-862`). **SQLite silently ignores that pragma inside a transaction** —
   so the test is not "do the migrations still pass" but **"do those toggles execute outside
   a transaction."** If they do not, the rebuilds run with enforcement unexpectedly on or off
   and the guard is illusory.

## Phase 208: Onboarding Token Hardening

**Goal:** Make the invite safe to carry a human identity — *before* Phase 209 makes it do so.

**Requirements:** HAIA-10..14

| # | Defect | Evidence | Fix |
|---|---|---|---|
| 1 | **Replayable.** A `nonce` is generated but never stored or checked; only signature + `exp` are validated. | `agent-onboarding.ts:88, 95-112` | Persist and consume the nonce |
| 2 | **Uncapped TTL.** `ttlMinutes: 525600` mints a one-year token. | `invite/route.ts:52, 66` | Server-side cap, 15–60 min |
| 3 | **Unscoped tokens work for any agent id.** Guard only fires on a non-empty list, so an invite minted without `--id` can register **any** id — including `alba`, `lcalderon-main-mac`, `oracle-1-droid`. | `register/route.ts:59`, `invite/route.ts:67` | Require non-empty `allowedAgentIds`; drop the `?.length` escape |
| 4 | **Revocation is reversible.** The upsert ends `ON CONFLICT(id) DO UPDATE SET … deregistered_at = NULL`, and register defaults `issueApiKey` true. Re-onboarding resurrects a revoked agent **and mints a fresh key**. | `agent-registry.ts:305`, `register/route.ts:43` | Split register from re-register |

**5 — the bypass that makes the other four insufficient.** All four defects above are scoped
to `/api/onboarding/*`. **`/api/agents/register` registers agents with no token at all** —
no nonce, no TTL, no `allowedAgentIds` — gated only by `authorizeRegistryWrite`
(`api/agents/register/route.ts:69`), which returns **true for any loopback request with no
credential** (`operator-auth.ts:35-37`). It accepts caller-supplied `capabilities` (`:52-53`)
and **mints an API key by default** (`:64`, `issueApiKey: body.issueApiKey !== false`).

Without closing this, Phase 209's "`ownerUserId` required for new registrations" ships with a
day-one bypass, and P1 is unenforceable. **This route must be brought under the same regime
as the onboarding path**: owner required, capabilities not caller-supplied, key issuance not
default-on, and loopback alone insufficient for registry writes.

**Success Criteria:** all five fixed, plus regression tests written **as attacks**, not happy
paths. 3 + 4 compose into the worst case — take over a trusted agent id, then survive its
revocation — so land them together. 5 is independently sufficient to defeat P1, so it is not
optional.

**Also noted:** `invite/route.ts:41-47` authorizes *either* an operator session *or*
`authorizeRegistryWrite`. The second branch has no user session, so Phase 209's `ownerUserId`
cannot be derived from the caller there. Either close that branch for owner-bearing invites
or record the owner as caller-asserted.

## Phase 209: Human Accountability Binding — **P1**

**Goal:** Every agent points at the human it acts for.

**Requirements:** HAIA-15..19

**Success Criteria:**
1. `registered_agents` gains `owner_user_id TEXT REFERENCES users(id) ON DELETE CASCADE` +
   index. *(Table is `registered_agents`, `db-schema.ts:2871` — there is no `agents` table.)*
   This is the **only** new schema the identity model requires; the cascade on the other side
   already exists (`agent_api_keys.agent_id → registered_agents ON DELETE CASCADE`,
   `db-schema.ts:2904`). Delete a user → agents → keys, in one step.
2. `ownerUserId` carried through `AgentOnboardingTokenPayload` and `RegisterAgentInput`;
   **required** for new registrations.
3. **Unowned agents fail closed** (P1) **at an enforcing boundary, not merely in a migration.**
   A backfill plus a service allowlist does *not* satisfy P1 on its own: all **58**
   `authenticateAgentHeaders` call sites would still accept an unowned agent holding a valid
   key, and `/mcp` (Phase 211) does not exist yet. This phase must either land the
   owner check inside `authenticateAgentHeaders` itself — accepting the 58-site blast radius
   and the CI gate — or explicitly record that P1 is unenforced until Phase 211, and not
   claim otherwise. The 59 existing agents are backfilled with an explicit migration; service
   agents get a documented allowlist. **Free today** — zero live keys.
4. Audit records `subject_user_id` **and** `actor_agent_id` — closing the two-parallel-trails
   problem (cloud app logs `user:<id>`, knowledge MCP logs `agent_id`).
5. `RegisteredAgent.role` is documented as a free-text *description* and is **never** an
   authorization input. RBAC comes from the bound user.
6. An agent with no owner is queryable as a defect state — feeds Phase 213.

## Phase 210: Three-Axis Permission Model — **P2 + P3**

**Goal:** Identity, clearance, and capability become three separate axes, with agent access
computed as an intersection with its owner.

**Requirements:** HAIA-20..25

**Scope is greenfield authorization work** — see the sizing finding above. This is the
largest and riskiest phase in the milestone. Split it.

### 210a — Server-authoritative grants + the human capability model

The prerequisite half. Today the two sides of P2's intersection are not even the same type:
agent grants are capability **strings** (`agent_capabilities`, `db-schema.ts:2918`) while
human grants are a **scalar** with `CHECK(role IN ('admin','operator','reviewer'))`
(`db-schema.ts:3483`). **You cannot intersect a string set with a rank.**

1. **Grants become server-authoritative.** Close the client-writable paths:
   `api/agents/register/route.ts:52-53`, the `parsed.input.capabilities` fallback at
   `api/onboarding/register/route.ts:67`, and `replaceCapabilities` (`agent-registry.ts:325`).
   A principal must not be able to declare its own capabilities — same defect class as
   declaring its own `MEMROOS_AGENT_ROLE`.
2. **Humans gain a capability representation** — schema, grant table, and a granting surface.
   This is new work, not a migration.
3. A real evaluator exists: `hasCapability(principal, capability)`. **None exists today.**
4. **It must not fail open.** `security-policy.ts:36-42` currently allows any agent with zero
   declared capabilities under `local-dev` or an env flag. Allow-on-empty is incompatible
   with P1–P3 and must be removed on the authenticated path.

### 210b — Clearance, intersection, and non-inheritance

5. **Clearance becomes a stored attribute** of users and agents, replacing `MEMROOS_AGENT_ROLE`
   as the input to the document-classification filter in
   `services/knowledge-mcp/knowledge_system/mcp_server.py` (~line 587; Phase 130 / MSIQ-02).
6. **P2 enforced by construction:** effective agent access = `agent grants ∩ owner grants`,
   computed in exactly one place, with a test proving an agent cannot exceed its owner on any
   axis.
7. **P3 enforced, with a named granting authority and a cap.** The principle is not satisfied
   by non-inheritance alone: if an owner may grant their agent whatever they hold, P3 is a
   slogan and the obvious test passes vacuously. Therefore record explicitly:
   - **who** may grant an agent clearance (proposal: the owner, for levels *strictly below*
     their own);
   - **what caps it** (proposal: reaching parity with the owner requires a second authority —
     an operator/admin approval — and is time-bounded rather than standing).
   - The test must be non-vacuous: prove not only that raising Eric's clearance leaves his
     agent unchanged, but that **Eric alone cannot raise his agent to his own level.**
   - Rationale in code comments: prompt injection, not bureaucracy. An agent reads untrusted
     text; a standing key to the vault is the thing being prevented.
8. **`ROLE_RANK` retirement is gated like Phase 211's boundary change.** There are **94**
   `requireRole`/`ROLE_RANK` references outside tests, including `proxy.ts:202,210,216` which
   gates admin/operator/reviewer independently. Requires a CI gate, an enumerated consumer
   list, and a single-cutover plan. **Two authorization models running at once is how
   confused-deputy bugs happen** — do not leave both live.
9. **"CEO" is expressed as clearance, not as `admin`.** `ROLE_RANK` is strictly linear, so any
   new tier lands either above `admin` (more than admin) or below `operator` (less than the
   ask). Eric must not be made `admin` — that grants key issuance, policy changes, and other
   users' data.
10. Least privilege becomes expressible: a sync agent that needs only "read Linear" gets
    exactly that, not a rank implying everything beneath it. With 59 agents this stops being
    theoretical.

**Known hazard for the intersection:** `space_members` (`db-schema.ts:472-479`) has
`PRIMARY KEY (space_id, member_id)` with `member_type IN ('human','agent')` and **no foreign
key on `member_id`** — humans and agents share one id namespace. Any P2 intersection computed
over space membership inherits that collision risk.

## Phase 211: Authenticating MCP Boundary

**Goal:** The server derives the principal from the credential and ignores what the client
claims.

**Requirements:** HAIA-26..29

**Scope warning — read before estimating.** `authenticateAgentHeaders` is **not** an unused
helper: **58 call sites** plus a CI boundary gate (`scripts/check-route-auth-boundary.mjs`).
Any semantic change — rejecting deregistered agents, resolving an owner, failing closed on a
null owner — propagates to all of them.

**Success Criteria:**
1. `POST /mcp` exists. Onboarding has been advertising `${memroosUrl}/mcp`
   (`agent-onboarding.ts:83`) while **no route serves it** — 239 `route.ts` files, zero
   matches, no rewrite, no middleware.
2. Resolves bearer → `authenticateAgentKey` → agent → `owner_user_id` → user → clearance and
   capabilities. **Ignores client-supplied `MEMROOS_AGENT_ID` and `MEMROOS_AGENT_ROLE`.**
   Client values may pass only as `agentIdHint`, which `agent-registry.ts:455` uses solely to
   *reject* on mismatch, never to select.
3. Agent id is read from the authenticated DB row, **never** parsed from the key string —
   `generateApiKey` embeds the id (`agent-registry.ts:110-111`) but that substring is not
   authenticated.
4. Identity re-resolved per request; no indefinite token→identity caching, so revocation and
   `deregistered_at` take effect immediately.
5. **`services/knowledge-mcp` rejects client-declared identity — both channels.** Rejecting
   the env var is **not sufficient**: in
   `services/knowledge-mcp/knowledge_system/mcp_server.py`, `_memroos_agent_id` (~line 340)
   and `_memroos_agent_role` (~line 354) each take an **explicit tool argument that takes
   precedence over the env var** — `return (agent_id or os.environ.get(...) or "shared")`.
   A client can therefore still name its own id and clearance via the tool call after the env
   var is ignored. **Both channels must be closed on the authenticated path**, and `"shared"`
   must become a hard error rather than a silent default. Two identity resolvers in one
   process — one authenticated, one not — is the confused-deputy condition.
6. The CI boundary gate is updated deliberately and all 58 call sites re-verified.

## Phase 212: Credential Delivery

**Requirements:** HAIA-30..32

### 212a — spike first (gates 205b)

`claude mcp add` accepts `--client-id`, `--client-secret`, `--callback-port`: **Claude Code
speaks OAuth to MCP servers.** If MemroOS were an OAuth resource server, Eric's Claude Code
would open a browser, he would sign in **with Google**, and the agent would hold a
short-lived token minted against his verified human identity — instead of a static bearer
token in a config file indefinitely. Materially better, and it may replace 205b entirely.

Does **not** contradict the standing constraint: binding to his *Anthropic* account remains
impossible; this binds to *our* IdP. Nango cannot help — it is an OAuth *client*; this needs
an authorization *server*.

**Output:** go/no-go plus an effort estimate for the MCP authorization spec.

### 212b — static bearer (only if 205a is no-go)

1. `buildMemroosMcpConfig` emits `type: "http"` + `Authorization: Bearer`; the minted key is
   threaded from `registerAgent`.
2. **Six emission sites in the installer, not one.** `script/route.ts:121` extracts only
   `mcpServers["memroos"]["url"]` and reconstructs four entry shapes locally
   (`generic_entry`, `http_entry`, `streamable_entry`, `http_url_entry`); the Hermes path
   hand-writes YAML with only `url:`. Changing the server-side builder alone reaches **zero**
   clients.
3. `claude mcp add --transport http memroos <url> --header "Authorization: Bearer <key>"`
   verified end-to-end. `--header` is confirmed supported and appears in Claude Code's own
   documented examples.
4. 0600 handling retained; prefer env-var interpolation where a client supports it.

## Phase 213: Governance UI

**Requirements:** HAIA-33..36

**Success Criteria:**
1. A users list — none exists today.
2. An agents list showing **the owning human** for each, with **unowned agents surfaced as a
   defect state** (P1), not hidden behind a null.
3. Issue and revoke agent credentials, including the invite one-liner.
4. **Effective access view**: for a human or agent — identity, clearance, capabilities, and
   for an agent, the intersection with its owner (P2) and its independently-granted clearance
   (P3).
5. **Offboarding blast radius**: disable a human and see every agent that dies with them.
6. Security state from Phase 213: key age, `expires_at`, `last_used_at`, revoked status.

**Scope:** the management surface for identity and access, not a general admin console.
`/agents` exists as a page and is the natural host.
