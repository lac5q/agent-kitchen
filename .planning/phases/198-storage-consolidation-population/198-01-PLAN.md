# Phase 198: Storage Consolidation Decision + Population Cron (STORECON-01..05)

**Phase ID:** 198
**Milestone:** v8.31 Operator Config Durability + Storage Consolidation
**Date added:** 2026-07-26
**Status:** PLANNED
**Depends on:** CFGDUR-05 (liveness monitoring, which must cover the new population jobs)

## Goal

Two related problems, deliberately in one phase because the second changes the
inputs to the first.

1. Decide whether the operator's SQLite kernel should move to managed Postgres.
2. Fix the fact that nothing is currently *generating* embeddings or graph
   projections — only checking that the backends are reachable.

The order matters: restoring embedding generation changes the growth rate that
the storage decision depends on. Measuring first and deciding on a frozen
dataset would produce a decision keyed to the wrong number.

## Operator decision (2026-07-26) — STORECON-03 provider is CHOSEN

**Ollama `nomic-embed-text`, running on oracle-1. $0 per call.**

This restores the original v8.15 CLOUDOPS-01 plan, which specified exactly this
and was never completed. Rejected: OpenAI embeddings — a recurring per-call bill
that scales with memory volume, on a cost-conscious operator, for a quality
delta that is not the current bottleneck.

Cost of this choice is disk and RAM on a host that hit 89% used three days ago:
`nomic-embed-text` is ~275MB, plus Ollama's runtime footprint. **Disk headroom
must be verified before the pull, and the model must not be pulled if it would
drop free space below the `memroos-disk-watch` warn threshold (6GB).** That
check is a hard gate, not a courtesy.

## Sub-IDs (acceptance criteria)

### STORECON-01 — Sizing baseline before any decision

- Captured and committed: `conversations.db` on-disk size, its ten largest
  tables by byte count, observed growth rate, oracle-1 free-space headroom, and
  the Supabase tier this workload would land in.
- Measured **after** STORECON-03 lands, so the growth rate reflects live
  embedding generation rather than a frozen migrated corpus.
- Read-only. No schema changes, no `VACUUM` (which rewrites the whole DB and is
  not free on a disk-constrained host).

### STORECON-02 — ADR with the premise corrected

- An ADR records the decision and explicitly corrects the premise that
  motivated it. The stated goal was "maximize use of space."
  **Running Postgres locally on oracle-1 would consume MORE disk than SQLite
  does today** — WAL, per-index overhead, and a server process, versus a single
  embedded file. Only a *managed/remote* Postgres (Supabase) reduces local
  footprint, and it does so by moving the data off-host, which introduces
  network dependency and egress on a memory system whose reads are hot.
- The ADR states which of those it is choosing and why, and names the option of
  changing nothing as a legitimate outcome.
- No migration is executed under this phase regardless of the decision.

### STORECON-03 — Restore embedding generation — **provider CHOSEN**

- Ollama installed on oracle-1 (aarch64); `nomic-embed-text` pulled; embed
  smoke test succeeds. This closes the v8.15 CLOUDOPS-01 criterion that was
  never met.
- **Hard gate:** verify ≥6GB free before pulling. Abort if not.
- The app's embedding provider is configured and the embedding job is scheduled.
  Current state is `[embeddings] provider disabled; embedding job not
  scheduled` — no provider key on either the `memroos` or `mem0` container.
- Verified by embedding count increasing on new content, not merely by the
  provider reporting configured. `message_embeddings` was 45,750 at migration;
  a later count must exceed it after new messages land.
- Dimension compatibility with the existing Qdrant collections is checked
  **before** writing. `nomic-embed-text` is 768-dim; existing collections were
  populated by whatever produced the migrated vectors. A mismatch means a new
  collection, not a silent corrupting write into an existing one. (Prior art:
  the 2026-03-21 mem0/Gemini 768-vs-3072 dimension incident.)

### STORECON-04 — Diagnose `graph-catchup projected: 0`

- The cause is identified and labelled either benign (genuinely caught up) or a
  defect with a fix.
- This has been carried as "ambiguous" across multiple sessions. The ambiguity
  is itself the defect being closed — it may not be deferred again.
- Note the likely coupling: if graph projection depends on embeddings,
  STORECON-03 may resolve this as a side effect. That must be *verified*, not
  assumed — a `projected: 0` that persists after embeddings are live is a
  different bug.

### STORECON-05 — Jobs that populate, not just check

- Scheduled jobs that write to Qdrant and Neo4j exist, are documented, and their
  liveness is covered by CFGDUR-05.
- The distinction being enforced: the v8.15 health check proves the backends are
  *reachable*. Reachability is not evidence that anything is being written. Both
  were green throughout the period when nothing was being generated.
- Each job emits a durable success signal (heartbeat file or log line) that the
  liveness check reads.

## Out of scope

- **Executing any Supabase project deletion.** The operator confirmed a cleanup
  (delete ApplyPilot's project; export JobHunt's data locally then delete;
  leave GrowthAlchemyLab untouched). That confirmation predates several context
  compactions and is irreversible. Re-confirm immediately before execution.
  Deliberately excluded from any "implement everything" sweep.
- Migrating the SQLite data anywhere. This phase decides; an approved migration
  is its own phase, gated on a verified restore rehearsal.
- Replacing mem0/Qdrant/Neo4j as backends — approval-gated per
  `.planning/MILESTONES.md` § Deferred / Approval-Gated.
- Voyage embeddings (v8.15 Phase 166) — remains out of scope.

## Risks

- **Disk.** Ollama + model on a host that recently hit crit. The ≥6GB gate is
  mandatory and the disk-watch timer must be confirmed armed before starting.
- **Dimension mismatch silently corrupting a populated collection.** 43,305
  points in `knowledge_docs` are real migrated data. Verify dimensions before
  the first write; write to a new collection if they differ.
- **RAM contention.** oracle-1 is 10Gi total running Next + mem0 + SQLite.
  v8.15 budgeted for nomic specifically, but that budget predates the current
  workload; confirm headroom under load, not at idle.
