# Phase 186: cordant-hermes-01 Parity (HOSTPAR-01..04)

**Phase ID:** 186
**Milestone:** v8.27 Operator Config Durability + Storage Consolidation
**Date added:** 2026-07-26
**Status:** PLANNED
**Depends on:** Phase 185 (the durability mechanism and health check this phase deploys)

## Goal

cordant-hermes-01 is the v8.21 deploy target and the least-observed host in the
fleet. It received none of the protective tooling from the oracle-1 session and
runs its own local Neo4j rather than Aura.

## Operator decision (2026-07-26) — HOSTPAR-04 is CLOSED

**cordant-hermes-01 stays on local Neo4j. This is intentional, not drift.**

Rationale: migrating it to Aura would mean a data migration on a host that has
not been backed up in this session, which is exactly the risk the standing
no-data-loss rule exists to prevent. The benefit (one shared graph) does not
justify it now. This phase therefore *observes and records* rather than moves.

The direct consequence for HOSTPAR-02: the health check must be host-aware. A
running local `neo4j` container is a **failure** on oracle-1 and **correct** on
cordant-hermes-01. A check hardcoded to oracle-1's expectations would alert
continuously here and get muted — which is worse than no check.

## Sub-IDs (acceptance criteria)

### HOSTPAR-01 — Per-host inventory

- A committed document records, for each of oracle-1 and cordant-hermes-01:
  graph backend, vector backend, SQLite path, restart path, monitoring
  coverage, alert destination, and whether each divergence is intentional.
- Divergence is allowed. Undocumented divergence is the defect.
- The Aura-vs-local split is recorded as intentional per the decision above.

### HOSTPAR-02 — Host-aware durability + health check

- Phase 185's host profile and health check run on cordant-hermes-01 with
  expectations drawn from that host's profile, not oracle-1's.
- Specifically: `expected_graph_backend: local` here vs `aura` on oracle-1. The
  check asserts *conformance to the declared profile*, not a fixed topology.
- Verified by injecting drift in both directions on a disposable host: a host
  declaring `aura` that resolves local must alert, and a host declaring `local`
  that resolves local must not.

### HOSTPAR-03 — Liveness monitoring

- CFGDUR-05 timer/cron liveness coverage extends to this host.
- Same rule: assert recency of last successful run, not `is-enabled`.

### HOSTPAR-04 — Aura-vs-local decision — **CLOSED 2026-07-26**

- Decision: stay on local Neo4j. Recorded above with rationale.
- Revisit trigger: if cross-host graph recall becomes a requirement, or if this
  host gains a verified backup/restore rehearsal, reopen.

## Out of scope

- Migrating any data off or onto this host.
- The v8.20 `CONNMEM-LIVE-DEFER` Linear/Circleback credential work, which also
  targets this host but is a separate concern.
- Changing this host's role as the v8.21 deploy target.

## Risks

- This host has no verified backup. Any change lands read-only first
  (inventory, monitoring), and nothing mutates state without a snapshot.
- Deploying a check tuned for the wrong host produces constant false alerts and
  trains the operator to ignore them. HOSTPAR-02's bidirectional drift test
  exists specifically to prevent that.
