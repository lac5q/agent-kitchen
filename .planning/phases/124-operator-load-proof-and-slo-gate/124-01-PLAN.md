# 124-01 Plan: Operator Load Proof + SLO Gate

## Objective

Prove the hosted operator's capacity rather than asserting it. Ship a committed, repeatable load-test harness that simulates 100 agents at 1,000 `knowledge_write` calls/hour against an operator endpoint, produces a signed report (p95 < 500ms, error rate < 0.1%), runs on demand and on a schedule, and gates all enterprise-readiness / SKU claims in CI and the NOC the same way `check:future-spikes` gates spike-adoption claims.

The operator URL is **config-driven** (`MEMROOS_LOADTEST_URL`, default `http://localhost:3002`) so CI runs against local staging and the operator can point it anywhere, including production under explicit operator control.

## Scope

- A load-test harness script that drives 100 concurrent simulated agents.
- A signed report writer (JSON + human-readable markdown) with p95 latency, error rate, throughput.
- A CI gate (`check:operator-load-slo`) that blocks enterprise-readiness claims when the latest report fails or is stale.
- A NOC/operator surface showing the latest load-test status.
- An honest-degradation mode: if the operator URL is unreachable, the harness fails loudly with a receipt — never silently passes.

## Non-Goals

- No load-testing production without explicit operator approval (the harness defaults to localhost; production runs are opt-in via env).
- No new hosted infrastructure — this phase proves the *existing* operator, it does not build a new service.
- No multi-tenant vault isolation (that is Phase 125, ENTOPS-02/03) — this harness targets the operator's `knowledge_write` surface as it exists today.
- No real agent runtimes — simulated agents issuing HTTP `knowledge_write` calls.
- No paid load-testing SaaS (k6 cloud, Loader.io, etc.) — MIT/OSS only, per the standing gate.

## Existing surfaces this builds on (verified 2026-07-06)

- **`scripts/check-future-spikes.mjs`** — the gate pattern to copy: a Node checker that validates a report file and fails CI if claims outrun proof.
- **`npm run check:future-spikes`** — wired into `.github/workflows/ci.yml` after lint.
- **`apps/memroos/src/app/api/...`** — the operator's HTTP surface; the harness targets whichever route backs `knowledge_write`. (Knowledge MCP is a separate Python service — see note below.)
- **`.github/workflows/ci.yml`** — add an `operator-load-slo` job next to `recall-canary`.
- **NOC aggregation** — `/api/operations/noc` pattern for surfacing a new health signal.

**Important routing note:** the `knowledge_write` MCP tool lives in the **Python** `services/knowledge-mcp/` service, not the Next.js app. The harness must target whichever HTTP surface the operator exposes for durable knowledge writes. If the only path today is the MCP tool (stdio), the harness targets the operator's REST proxy if one exists; if none exists, this phase's deliverable narrows to (a) the harness framework + (b) an explicit finding that a REST knowledge-write surface is needed for hosted load-testing, recorded as a Phase 125 dependency. The worker must verify the actual endpoint before writing the report — do not assume.

## Design Contract

### Load harness (`scripts/operator-load-test.mjs`, NEW)

```
Usage: node scripts/operator-load-test.mjs [--agents 100] [--writes-per-hour 1000] [--duration 300s] [--url $MEMROOS_LOADTEST_URL]
Defaults: agents=100, writes-per-hour=1000, duration=300s, url=http://localhost:3002
```

- Spawns N concurrent simulated agents (Node workers / promise pools, no external deps beyond what's in package.json).
- Each agent issues `knowledge_write`-equivalent HTTP POSTs at the calculated rate (`writesPerHour / 3600` per agent per second).
- Collects per-request latency + status; computes p50/p95/p99, error rate, throughput, start/end, target URL (host only, no auth header in report).
- Writes `reports/operator-load/latest.json` + `latest.md` with a signed manifest (sha256 of the JSON, plus the git SHA and a timestamp).
- Honest degradation: if the URL is unreachable, writes a `latest.json` with `status: "unreachable"` and exits non-zero.

### SLO gate (`scripts/check-operator-load-slo.mjs`, NEW)

- Reads `reports/operator-load/latest.json`.
- Fails if: report missing, `status !== "pass"`, `p95Ms >= 500`, `errorRate >= 0.001`, or report is older than `OPERATOR_LOAD_MAX_AGE_HOURS` (default 72).
- Mirrors `check-future-spikes.mjs` structure.

### Enterprise-claim gate

Any markdown/doc/landing copy that asserts "enterprise-ready", "100-agent", "SOC2", "multi-tenant", or similar must be allowed by the gate. The checker greps `content/`, `docs/`, and `README*` for a fixed claim vocabulary and fails if a claim is present but the latest load report is not green. (Start with a small, explicit vocabulary list in the script; operator can extend.)

### CI wiring

```yaml
# .github/workflows/ci.yml — new job
operator-load-slo:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - run: npm ci
    - run: node scripts/check-operator-load-slo.mjs
```

A *scheduled* run that actually executes the harness against a staging operator is a follow-on (needs a staging URL secret); the CI job by default only checks the committed report's freshness/SLO. On-demand local runs execute the harness directly.

### NOC surface

Add an `operatorLoadStatus` block to `/api/operations/noc` summarizing the latest report (p95, error rate, status, age). Render in the existing Operations UI as a card.

**Verification commands:**

```bash
# Unit-test the gate (no live operator needed)
node --test scripts/__tests__/operator-load-slo.test.ts
# or npx vitest if colocated

# Gate against a committed baseline report
npm run check:operator-load-slo

# Live local run (operator must be up on localhost:3002)
node scripts/operator-load-test.mjs --duration 60s
```

**Success criteria mapped to requirements (ENTOPS-01):**
1. Harness runs 100 simulated agents at 1,000 writes/hour for the configured duration and emits a signed JSON+MD report with p95/error-rate/throughput. Test: run against a local temp mock operator and assert the report shape + signing.
2. Harness is runnable on demand (`node scripts/operator-load-test.mjs`) and the gate runs in CI (`check:operator-load-slo` job green when a valid fresh report exists, red when stale/failed/missing).
3. Enterprise-readiness claim vocabulary is blocked by the gate until the latest report is green — test with a fixture doc containing a claim and a missing report.

**Escalation triggers (route to Watcher):**
- Any change that lets the gate pass without a real report (e.g., hardcoded `status: pass`).
- Auth tokens or secrets written into a committed report.
- The harness silently passing when the operator is unreachable.
