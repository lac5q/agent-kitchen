# 122-01 Plan: Belief Promotion Pipeline

## Objective

Give MemRoOS a governed promotion pipeline that moves memories bronze → silver → gold only through explicit, deterministic checks (provenance, freshness, policy/label clearance, conflict scan, dedupe), with auditable receipts, demotion (gold → silver with a visible reason when a source is invalidated or contradicted), and a human-review queue for high-stakes claim categories before they reach gold.

Today belief stage is a runtime-only label on recollection candidates (`BeliefStage` in `apps/memroos/src/lib/recollection-policy.ts`). Nothing persists it, nothing gates promotion, nothing demotes. This phase builds the persisted, fail-closed promotion machinery.

## Scope

- Persist a belief stage on memory candidates so it survives across runs.
- Implement a deterministic promotion check pipeline (no LLM-only admission).
- Emit auditable promotion/demotion receipts.
- Demote gold → silver when a source is invalidated or a conflict is detected.
- Route high-stakes categories to a human-review queue for gold admission.
- Policy-configurable category list; fail-closed for unlisted sensitive labels.

## Non-Goals

- No LLM judgment as a sole admission path (BELIEF-01 is explicit on this).
- No automatic gold promotion of high-stakes categories — human review is mandatory.
- No new memory backend (build on the existing `agent_memory_candidates` table).
- No changes to the recollection context-pack path (that consumes belief stage read-only; Phase 123 handles outbound gating).
- No raw sensitive payloads in promotion receipts.
- No cross-tenant promotion.

### Promotion check pipeline (`evaluatePromotionChecks`)

Pure function, deterministic, no LLM. Each check returns `{name, pass: boolean, evidence}`:

1. **provenance** — candidate has a source pointer / capture_id with a non-null hash. `pass = !!sourceHash`.
2. **freshness** — source `verified_at` (or `created_at` fallback) within `BELIEF_FRESHNESS_DAYS` (default 180, env-overridable). `pass = ageDays <= limit`.
3. **policy** — `authorizeMemoryUse({ actor, purpose: 'promotion', label })` returns `allow`. `pass = decision === 'allow'`.
4. **conflict** — scan existing gold candidates in the same tenant for a `content_hash` match OR a semantic conflict (start with hash/dedupe match only; semantic conflict deferred to a later phase with eval proof). `pass = !conflictHit`.
5. **dedupe** — no existing gold candidate with same `content_hash`. `pass = !dupeHit`.

### Admission gate (fail-closed, code-level)

```ts
// Silver → Gold admission. No path bypasses this.
function canAdmitToGold(checks: PromotionChecks, category: ClaimCategory, config: BeliefConfig): AdmissionDecision {
  const allChecksPass = checks.every(c => c.pass);
  if (!allChecksPass) return { kind: 'denied', reason: 'one_or_more_checks_failed', failedChecks };
  if (isHighStakesCategory(category, config)) {
    return { kind: 'queued_for_review', reason: 'high_stakes_category_requires_human_review' };
  }
  return { kind: 'admitted' };
}
```

- High-stakes category list is **config** (default: `pricing, product_capability, legal_compliance, personal_data`). Unlisted sensitive labels (per MEMSEC sensitivity) **fail closed** → queue.
- There is NO `kind: 'admitted'` path that skips `canAdmitToGold`. The DB UPDATE that sets `belief_stage = 'gold_operational_truth'` runs inside a transaction that first inserts the `belief_promotion_decisions` row with `decision = 'admitted'` — mirroring the dispatch SQL gate, the admission is structurally inseparable from the receipt.

### Demotion (BELIEF-02)

Two triggers:
1. **Source invalidated** — a gold candidate whose source is deleted/expired → demote to silver with `demotion_reason = 'source_invalidated'`.
2. **Conflict detected** — a new gold admission conflicts with an existing gold → the older one demotes with `demotion_reason = 'superseded_by_conflict'` (S5 scenario).

Demotion writes a `belief_promotion_decisions` row (`decision = 'demoted'`, `from_stage = gold`, `to_stage = silver`) and updates the candidate. Demotion is the one path that does NOT require human review even for high-stakes categories — demoting is always safe.

### Human-review queue (BELIEF-03)

- `enqueueForReview(candidateId, category)` inserts into `belief_review_queue`.
- `resolveReview(queueId, resolution, operatorId)` — only `'approved'` moves the candidate to gold (re-runs `canAdmitToGold` which now returns `admitted` because the review flag satisfies the high-stakes gate); `'rejected'` marks the candidate `status = rejected`.
- API: `POST /api/belief/review/{id}/resolve` (operator auth via existing `authorizeOperatorWrite`).
