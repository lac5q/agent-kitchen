## Goal

Make the oracle-1 configuration fixes structural instead of conventional.

The Aura disconnection was not caused by a bug. It was caused by a correct
`docker compose` invocation that happened to omit a host-only file, on a system
where omitting that file silently produces a *working but wrong* stack. The app
started, served traffic, and wrote graph data — to the wrong place. There was no
error, no degraded-health signal, and no alert. It was found by accident months
later.

The current mitigation is a wrapper script plus operator discipline. That is the
same class of control that already failed once. This phase replaces it with
something that does not depend on remembering.

## Non-negotiable constraint

No step in this phase may lose users, configuration, or memory/data on any host.
Where a change cannot be made without risking that, the change stops and the
phase reports blocked. This is the operator's standing rule and it outranks
every success criterion below.

## Sub-IDs (acceptance criteria)

### CFGDUR-01 — Version the host topology, not the secrets

- Which backends a host uses (Aura vs local Neo4j; Qdrant Cloud vs local) is
  declared in a committed, non-secret artifact — a host profile — rather than in
  a gitignored file that exists on exactly one machine and has no backup.
- Secrets (Aura password, Qdrant API key, SendGrid key) continue to load from
  `.env` / 1Password. Nothing secret enters git. `grep` for known credential
  patterns over the committed profile returns zero hits.
- The oracle-1 profile reproduces today's working topology exactly: Aura HTTP
  URL, Qdrant Cloud URL, local `neo4j` service excluded.
- Applying the profile to a host that is already correct is a no-op. This is
  verified before it is applied to oracle-1, on a disposable host.

### CFGDUR-02 — Make the wrong command impossible, not just discouraged

- A plain `docker compose -f docker-compose.local.yml up -d` on oracle-1 either
  (a) yields the Aura + Qdrant Cloud topology, or (b) refuses to start with an
  error naming the missing profile and the command to fix it.
- "It works if you use `scripts/memroos-restart.sh`" does **not** satisfy this
  criterion. The failure being designed out is a human running the documented
  upstream command.
- **Measured on oracle-1 2026-07-26 — `COMPOSE_FILE` does NOT solve this.** An
  explicit `-f` on the command line overrides both the automatic
  `docker-compose.override.yml` pickup *and* the `COMPOSE_FILE` environment
  variable. Compose v5.3.0 on oracle-1, minimal two-file fixture:

  | invocation | resolved `NEO4J_HTTP_URL` |
  |---|---|
  | `docker compose -f docker-compose.local.yml config` | `http://local-neo4j:7474` ❌ |
  | `COMPOSE_FILE=local:override docker compose -f docker-compose.local.yml config` | `http://local-neo4j:7474` ❌ |
  | `COMPOSE_FILE=local:override docker compose config` | `https://aura.databases.neo4j.io` ✅ |

  The outage command was `docker compose -f docker-compose.local.yml up -d` —
  row 2. An env-var-based control cannot defend against it, because the flag
  wins by design.
- **Therefore the app-side startup assertion is the PRIMARY control, not the
  fallback.** The app must, at boot, compare its resolved backends against the
  declared host profile and refuse to serve (or hard-fail health) on mismatch.
  This is the only mechanism that survives an arbitrary `-f` invocation.
  `COMPOSE_FILE` in the host `.env` is still worth setting as a convenience for
  the no-flag path, but it must not be represented as the guarantee.
- Documentation must stop presenting `-f docker-compose.local.yml` as the
  canonical start command anywhere it appears, since that is literally the
  failing invocation.

### CFGDUR-03 — Commit the health check and test it

- `scripts/memroos-health-check.sh` is committed to the repo. It currently
  exists only on oracle-1 and would not survive a host rebuild.
- Its failure branches have tests: Aura env drift, Qdrant placeholder/unset,
  Qdrant unreachable (non-200), graph-catchup silent, DB unqueryable, `users`
  table empty, count regression vs. previous run, profile artifact missing,
  local `neo4j` container running.
- The count-regression check compares against the **previous run**, not an
  all-time floor. A floor never rises to track legitimate growth, so a wipe from
  a recent high down to just above the floor goes undetected. The state file
  is overwritten unconditionally each run; a legitimate deletion alerts once and
  re-baselines.
- The DB is opened `{ readonly: true }`. A monitoring check must not be capable
  of mutating the thing it monitors.
- Documented: what each check asserts, what it cannot detect, and the alert
  destination.

### CFGDUR-04 — Reconcile the two health systems

**Operator decision 2026-07-26: keep systemd+GitHub-issues, retire cron+SendGrid.**

Rationale: the Python/systemd system already dedups into GitHub issues with a 6h
cooldown per failure signature, has a valid token at `/etc/memroos/gh-token`, and
produces a durable, searchable record rather than an email that gets archived.
The cron+bash+SendGrid job is the one that exists only on the host and would not
survive a rebuild.

Migration order matters and is non-negotiable: **port the checks first, verify
they fire, then remove the cron job.** Removing first leaves a coverage gap on
exactly the checks that were added because their absence caused an outage. The
checks to port are the ones this session added — users/registered_agents count
regression, override/profile presence, local-neo4j-not-running, Aura env
conformance, Qdrant reachability.

- oracle-1 runs two independently-built monitors with overlapping coverage:
  cron → bash → SendGrid (15 min) and systemd timer → Python → GitHub issues
  (30 min, 6h dedup cooldown per failure signature, `/etc/memroos/gh-token`).
  Neither was aware of the other.
- One documented story results: for each check, which system owns it, which
  channel it alerts to, and why. Keeping both is a valid outcome; keeping both
  *undocumented* is not.
- Whatever is retired is removed from the host, not merely left disabled.

### CFGDUR-05 — Monitor the monitors

- An `enabled`-but-unarmed timer must alert. On 2026-07-23 both
  `memroos-healthcheck.timer` and `memroos-disk-watch.timer` stopped being
  scheduled while still reporting `enabled`; `systemctl list-timers` showed
  `NEXT: -`. They sat dead for three days. A check asserting `is-enabled` would
  have reported healthy the entire time.
- The liveness check therefore asserts *recency of last successful run* (via
  `list-timers` NEXT/LAST, or a heartbeat file each job touches), not
  configuration state.
- Cron jobs get equivalent coverage — a stale `health.log` mtime is the same
  failure with a different scheduler.
- The alert path for "the monitor is down" must not depend on the monitor that
  is down.

### CFGDUR-06 — Prove upgrades are non-destructive

- A regression runs the documented upgrade path on a disposable host seeded with
  users, registered agents, and a known config, then asserts: `users` > 0,
  `registered_agents` > 0, graph backend is Aura and not a local container,
  `QDRANT_URL` is not the placeholder, and the host profile survived.
- Extends `scripts/install-regression/install-regression.sh` and
  `.github/workflows/install-regression.yml` from v8.21 rather than starting a
  parallel harness.
- Runs against a disposable host only. It must never target oracle-1 or
  cordant-hermes-01.

## Risks

- **Applying a new config mechanism to a live operator host is itself the
  risk this phase exists to prevent.** Sequence: disposable host first, then a
  snapshot via the v8.24 recovery suite, then oracle-1, then verify counts.
- Retiring a health system could remove the only coverage for a check nobody
  realized it owned. CFGDUR-04's per-check ownership map must be complete
  *before* anything is removed.
- oracle-1 has limited disk headroom (recently 89% used). Any test that pulls
  images or writes large fixtures runs on the disposable host, not on oracle-1.
