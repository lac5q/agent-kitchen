# 131-01 Plan: Identity Lifecycle + Delegation Chains

## Objective

1. **TEAMSCALE-02 (Joiner)**: One operator action onboards a person with identity, role, space memberships, and agent kit (scoped keys, allowed skills), producing an onboarding receipt.
2. **TEAMSCALE-03 (Mover/Leaver)**: Offboarding revokes human + dependent-agent credentials atomically, reassigns owned artifacts, opens MEMLIFE review item, zero orphaned agents.
3. **TEAMSCALE-04 (Delegation chains)**: Verifiable user→agent→sub-agent chain preserved across A2A hops; policy evaluates weakest link.
4. **TEAMSCALE-05 (NOC views)**: Per-team NOC dashboard of memory growth, promotion queue, policy denials, skill usage, agent activity.
5. **TEAMSCALE-06 (Owner-gated assets)**: Named-owner approval gates on relationship-sensitive assets, enforced by POLGOV, visible in receipts.

## Design

### TEAMSCALE-02: Joiner flow (`identity/lifecycle.ts`)
- `onboardUser(db, {email, displayName, role, spaceIds, agentKit})` — atomic transaction: create user + role + space memberships + register agent + create agent API key. Returns `OnboardingReceipt {userId, agentId, agentApiKey, spaceIds, role, skills, createdAt}`.
- Audit: write an `AGENT_MATCHED` or custom audit row for the onboarding.

### TEAMSCALE-03: Mover/Leaver flow
- `offboardUser(db, userId)` — atomic transaction: revoke user_api_keys + user_refresh_tokens, deregister dependent agents, reassign owned artifacts (update owner_id to null or admin), open a MEMLIFE review item. Returns `OffboardingReceipt`.
- `scanOrphanedAgents(db)` — returns list of agents with live keys whose owner user is revoked/deleted. Zero = pass.

### TEAMSCALE-04: Delegation chains (`identity/delegation.ts`)
- `DelegationChain` type: `{user: {id, role}, agent: {id, capabilities}, subAgent?: {id, capabilities}, hops: DelegationHop[]}`.
- `buildDelegationChain(userId, agentId, subAgentId?)` — constructs the chain from DB.
- `verifyDelegationChain(chain)` — validates each hop.
- `weakestLinkOutcome(chain, baseOutcome)` — policy evaluates the weakest link: if any hop has a deny, the chain is deny.
- Integration: the policy engine's dimension rules can check delegation chain presence.

### TEAMSCALE-05: NOC views (`identity/noc-views.ts`)
- `getTeamNocView(db, {spaceId, window})` — returns `{memoryGrowth, promotionQueueDepth, policyDenials, skillUsage, agentActivity}`.
- Queries: count messages by space in window, count belief promotion queue items, count POLICY_DECISION audit rows with outcome=deny, aggregate skill reports, count agent heartbeats.

### TEAMSCALE-06: Owner-gated assets (`identity/owner-gate.ts`)
- `OwnerGate` type: `{assetType, assetId, ownerId, approvalMode: "standing" | "per-use"}`.
- `checkOwnerGate(db, {assetType, assetId, requestingAgentId, ownerId})` — checks if the owner has standing approval or has granted per-use approval.
- Integration with policy engine: a dimension rule with `object.ontologyType: ["relationship_asset"]` + custom owner-gate check.
- `grantStandingApproval(db, {ownerId, assetType, assetId})` and `grantPerUseApproval(db, {ownerId, assetType, assetId, agentId})`.
- Audit: owner-gate decisions visible in POLICY_DECISION receipts.
