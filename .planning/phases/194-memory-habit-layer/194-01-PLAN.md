# 194-01 Plan: Habit Layer — Recall/Save Skills + Skill-Packs Bootstrap Fix

**Milestone:** v8.30 Seamless Memory Adoption
**Created:** 2026-07-26
**Depends on:** Phase 191 (the tool the skills teach), v8.6 Skill Trust Chain, skill-packs workspace
**Can run in parallel with:** Phases 192, 193
**Design:** `.planning/design/memory-adoption-v1.md`

## Progress

- Not started.

## Objective

Turn the probe-and-save contract into a habit that survives where hooks don't reach. Three surfaces carry it: auto-loading skills, the GSD workflow skills, and tool descriptions. First the delivery mechanism has to actually work — today the documented bootstrap returns nothing.

## Baseline (audited 2026-07-26)

- **The bootstrap is broken in a MemRoOS checkout.** `AGENTS.md` § "Agent Bootstrap Convention" tells every agent to call `knowledge_workspace_call("skill-packs","catalog",{"filter":"auto-load"})`. The catalog (`mcp_server.py:1220-1298`) merges `_skills_root_public()` = `$KNOWLEDGE_ROOT/skills` (`:248-250`) with `_skills_root_private()` = `$MEMROOS_PRIVATE_SKILLS_DIR` or `~/.memroos/skills` (`:253-258`). `KNOWLEDGE_ROOT` defaults to `.` (`:239`) and `memroos-mcp.sh:271-275` points it at `~/github/knowledge` if present else `$MEMROOS_ROOT`. **`$KNOWLEDGE_ROOT/skills` does not exist in this repo** — the repo's skills live in `.agents/skills/` and `docs/codex-cloud/skills/`, neither of which the catalog scans. The `auto-load` filter reads frontmatter `auto_load: true` (`:1259-1260`). `install` is a no-op returning advice text (`:1287-1295`).
- **Only one skill teaches a recall-then-save protocol, and it isn't shipped.** `docs/integrations/multica-memroos-skill.md` has exactly what's needed — "Recall relevant context: prefer MCP `memory_search` with issue title, repo, task goal" plus end-of-task `agent_memory_save` with type routing and required provenance keys — but it is a **doc**, has no `auto_load`, isn't in the catalog, isn't installed anywhere, and is scoped to Multica tasks. **This is the template.**
- `.agents/skills/memroos-save/SKILL.md` (v1.1.0) is strong on document writes — implicit-trigger list, path convention, mandatory frontmatter (`model`, `sources`, `derived_from`, `regen_prompt`), read-back verify, tell-user-the-path — and was written because of a real failure (`content/research/memroos-persist-failure-rca-2026-07-05.md`). It is fanned to 13+ harnesses by `install-agent-integrations.sh:376-388`. **But it never mentions `memory_save`, `agent_memory_save`, or `memory_recall`** — it is document-write only.
- **The GSD skills say nothing enforceable.** `docs/codex-cloud/skills/goal/SKILL.md` step 4 reads "Load relevant context from the repo, GSD state, and memory **if available**" — no tool named, no requirement. `beastmode-cloud`, `beastmode-qwen-cloud`, and `qwen-cloud` have neither recall nor save steps. Grep for `memory_recall|memory_save|memory_search|knowledge_search|agent_memory_save` across all of `docs/codex-cloud/skills/` returns **zero matches**.
- `knowledge_system_orientation` prompt exists at `mcp_server.py:1394` — an always-available surface that currently says nothing about the memory contract.
- Binding constraint: `agents/AGENTS_TEMPLATE.md` Skills > Memory (2026-07-09). These skills must reinforce that ordering, not undercut it.

## Scope

- Fix the skill-packs root resolution so the documented bootstrap resolves.
- Ship `memroos-recall` as a real auto-loading SKILL.md.
- Extend `memroos-save` to cover governed memory writes.
- Put a named, mandatory probe into the GSD skills.
- Encode the contract in tool descriptions and the orientation prompt.

## Non-Goals

- No new skill-distribution mechanism — reuse skill-packs + `install-agent-integrations.sh`.
- No bypass of the v8.6 skill trust chain (signing, provenance, pins) for new skills.
- No duplicating into MEMORY.md what a skill already says.
- No turning `install` into a real installer (out of scope).
- No changes to recall/save behavior itself — that's Phases 191/193.

## Design Contract

### D1 — Root resolution (MEMHABIT-01)

`_skills_root_public()` gains an ordered fallback: `$KNOWLEDGE_ROOT/skills` → `$MEMROOS_ROOT/.agents/skills` → repo-relative `.agents/skills`. First existing path wins; private root keeps precedence on name collision (unchanged). The resolved root is reported in `catalog` output so a wrong root is visible rather than silently empty. Add a test asserting the catalog is **non-empty from a clean MemRoOS checkout with `KNOWLEDGE_ROOT` unset** — the exact case that fails today.

### D2 — `memroos-recall` skill (MEMHABIT-02)

New `.agents/skills/memroos-recall/SKILL.md`, frontmatter `auto_load: true`, generalized from the Multica doc:

- **Start of task:** call `memory_prior_work` with the task statement plus repo/project. If it returns items, read the relevant ones via `fetch_ref` before planning. If it returns `search_skipped`, proceed — the receipt is the record.
- **Re-probe triggers:** topic shift, unexpected error, "have we seen this before?", any moment you're about to guess at a convention.
- **Belief-stage handling:** rely on `gold_operational_truth` directly; caveat `silver_candidate_claim` as a candidate; treat `bronze_raw_source` as evidence to cite, never as summarized truth.
- **Anti-patterns:** don't re-probe the same query repeatedly in one task; don't paste whole memories into context when a pointer suffices; don't treat an empty result as proof nothing exists if a tier was unhealthy (the receipt says which).

### D3 — `memroos-save` extension (MEMHABIT-03)

Add a memory-write section to the existing end-of-task checklist, keeping the document-write path intact:

| Content | Home |
|---|---|
| Repeatable procedure, class lesson, pitfall | **Skill** (SkillForge proposal) |
| Research deliverable, RCA, benchmark, comparison | **`knowledge_write`** (existing path) |
| Decision + its outcome, project fact, entity fact, handoff state | **`agent_memory_save`** (governed) |
| User-profile / environment invariant | memory, brief |

Include the Phase 193 rubric inline so the agent writes to threshold on the first try: state the outcome, scope to a project, name entities, include provenance.

### D4 — GSD skills (MEMHABIT-04)

`docs/codex-cloud/skills/goal/SKILL.md` step 4 changes from "load memory if available" to a named, mandatory `memory_prior_work` probe whose receipt id is recorded in the goal state. `beastmode-cloud`, `beastmode-qwen-cloud`, `qwen-cloud` gain a start-of-goal probe and an end-of-goal learnings write (or typed skip receipt). Phase 195's ADOPTTEL-03 gate enforces these; this phase writes them.

### D5 — Tool descriptions + orientation (MEMHABIT-05)

Memory-tool descriptions state when to call (Phase 191 D5 covers `memory_prior_work`; extend to `agent_memory_save` and `memory_recall`). `knowledge_system_orientation` gains a short memory-contract paragraph: probe at task start, governed save or typed skip receipt at task end, Skills > Memory for procedures. This is the floor that holds when neither hooks nor skills load.

## Risks

- **Root fallback masks misconfiguration.** If `$KNOWLEDGE_ROOT` is set but wrong, falling back could hide it. Mitigate by reporting the resolved root in catalog output and warning when the primary path was absent.
- **Skill sprawl.** A second memory skill risks contradicting `memroos-save`. Keep a strict split: `memroos-recall` owns reading, `memroos-save` owns writing; each cross-references rather than restating.
- **Auto-load context cost.** Two auto-loading skills consume context in every session. Keep both tight and measure; if they bloat, demote the reference detail to `references/*.md` and keep only the protocol in SKILL.md.
- **Prose still isn't enforcement.** This phase is the weakest lever in v8.30 by design — it only becomes reliable once Phase 192's hooks and Phase 195's gates exist. Don't count adoption as solved on the strength of skills alone.
