**Milestone:** v8.30 Seamless Memory Adoption

## Progress

- Not started.

## Objective

Make stored memory worth recalling. Today an agent can write vague, duplicate, or misfiled memory through an ungoverned path and nothing notices; and a well-formed candidate can sit at silver forever because promotion only ever runs by hand. This phase scores writes, coaches the agent in-band, closes the ungoverned path, and makes promotion happen on its own.

## Baseline (audited 2026-07-26)

- **Two write paths with different governance.** `agent_memory_save` (`mcp_server.py:868`) → `POST /api/memory/add` → `recordMemoryWrite()` (`lib/agent-registry.ts:478-505`) with policy check, audit row, `dedupHash` (`:493-503`), and `isRediscovery` via prior-hash lookup (`:154-171`). But `memory_save` (`mcp_server.py:843`) and `memory_search` (`:817`) post **directly to mem0** — no policy, no audit, no `memory_write` / `retrieval_trace` event. **The ungoverned pair is in `CORE_TOOLS` (`capabilities.py:13`); the governed one is not.**
- **Promotion machinery is complete but never runs.** `evaluatePromotionChecks` (`lib/belief/promotion.ts:476`) runs exactly five deterministic checks — provenance, freshness, policy, conflict, dedupe — with no LLM. `canAdmitToGold` (`:664`), `promoteCandidate` (`:1169`), `demoteCandidate`, `enqueueForReview`/`resolveReview`, hash-chained decision rows. Repo-wide, `promoteCandidate`/`canAdmitToGold` are called **only** from `lib/evals/belief-promotion-eval.ts` and the manual operator queue (`app/api/belief/queue`, `app/api/belief/review/[id]/resolve`). Captured sessions accumulate as silver indefinitely.
- **Salience misses agent memory.** `memory_salience` (`lib/db-schema.ts:2541-2555`) keys on `messages.id`; decay in `lib/memory-decay.ts` (`runDecay:185`, `startDecayScheduler:351`) with pinned/protected/policy_exempt skips. Agent-written memories and `agent_memory_candidates` have **no salience row**, so recall ranking cannot reinforce them.
- **No save-quality scoring exists.** The Memento spike says it plainly: *"The gap is not storage. The gap is a reusable save-quality report that scores candidate memory writes for type, source, dedupe hash, provenance, and promotion readiness."* Deferred, never built.
- Contradiction handling exists in three unconnected places: `conflictCheck` in `promotion.ts`, `lib/memory-consolidation.ts` (`ALLOWED_INSIGHT_TYPES` includes `contradiction`, `runConsolidation:37`, scheduler `:210`), and wiki-compiler tension linting.
- Binding constraint from `agents/AGENTS_TEMPLATE.md` (operator directive 2026-07-09): **Skills > Memory.** Procedures and class lessons belong in skills; memory is for user-profile/environment facts, decisions, outcomes, and handoff state. *"Everything else: skill first, memroos second, memory last (and brief)."*

## Scope

- Score every governed write; persist the score.
- Return coach-back receipts that teach the rubric in-band.
- Close the ungoverned default-visible path.
- Run the existing five promotion checks on a schedule.
- Extend salience coverage to agent memory and feed usefulness back.

## Non-Goals

- No LLM-only or hidden silver→gold promotion. The five deterministic checks remain the only gate.
- No new memory backend, no belief-schema change.
- No hard-rejecting merely low-quality writes — only policy violations fail closed.
- No auto-promotion of bronze straight to gold.
- Gold stays revocable and freshness-bound; this phase does not make anything permanent.
- No new contradiction engine — wire `conflictCheck` only.

## Design Contract

### D1 — Save-quality report (SAVEQ-01)

Computed on every governed write, persisted alongside it:

```json
{
  "score": 0.42,
  "threshold": 0.6,
  "components": {
    "type_fit": 0.5,
    "provenance": 1.0,
    "dedupe": 0.0,
    "specificity": 0.25,
    "promotion_readiness": 0.4
  },
  "flags": ["no_outcome_stated", "duplicate_of:mem_01H...", "procedure_belongs_in_skill"],
  "verdict": "accepted_with_coaching"
}
```

Components are deterministic and inspectable:

- **type_fit** — does the content match the declared memory type (`vector` / `episodic` / `graph`)?
- **provenance** — source ref, first-seen timestamp, derived-from present?
- **dedupe** — reuses the existing `dedupHash`; a hit sets `isRediscovery` (already wired to EFFTEL-05).
- **specificity** — outcome stated? project-scoped? entities named? not a bare restatement of the task?
- **promotion_readiness** — would `evaluatePromotionChecks` pass today, and if not, which check blocks?

### D2 — Coach-back, not rejection (SAVEQ-02)

Verdicts: `accepted` (≥ threshold), `accepted_with_coaching` (below threshold — **still stored**, with flags returned), `rejected` (policy violation only). Coach-back text is actionable and specific:

| Flag | Returned guidance |
|---|---|
| `no_outcome_stated` | "Add what happened as a result — a decision without its outcome can't be relied on later." |
| `duplicate_of:<id>` | "This already exists as `<id>`; flagged as rediscovery. Update that memory instead of adding a second copy." |
| `procedure_belongs_in_skill` | "This is a repeatable procedure. Propose a skill (SkillForge) — memory is for decisions, outcomes, and facts." |
| `no_provenance` | "Add source ref and derived-from; unsourced claims cannot be promoted past silver." |

`procedure_belongs_in_skill` is how the Skills > Memory ordering gets enforced mechanically instead of by exhortation.

### D3 — Governance parity (SAVEQ-03)

Decision D2 in the design doc: **route, don't remove** — less breakage for already-configured agents. `memory_save` and `memory_search` keep their names and signatures but their handlers proxy `/api/memory/add` and the Phase 191 recall path, gaining policy, audit, dedup, and telemetry. `agent_memory_save` joins `CORE_TOOLS`. Acceptance is stated as an invariant, testable by enumeration: **no MCP-visible tool writes memory without producing an audit row, and none searches without emitting a trace event.**

### D4 — Promotion scheduler (SAVEQ-04)

Follow the established scheduler shape (`startDecayScheduler` / `runConsolidation`). Per interval, select aging silver candidates (configurable min-age so fresh captures settle first), call `evaluatePromotionChecks`, then:

- all five pass → `promoteCandidate` → gold, hash-chained receipt
- `conflictCheck` fails → `enqueueForReview` (operator queue; never auto-resolved)
- freshness fails → leave silver, mark for decay
- provenance/policy fails → leave silver with a reason

Bounded per-run batch, structured run summary, idempotent. Zero LLM involvement.

### D5 — Salience for agent memory (SAVEQ-05)

Extend `memory_salience` so agent-written memories and `agent_memory_candidates` get rows (schema migration through the single `user_version` runner; coordinate with Phase 188 STORE-02 if that lands first). Feed `tool_record_outcome` usefulness signals into reinforcement so a memory that proved useful ranks higher next time — closing the "every call pays off" loop from the design doc, and satisfying the `NOC-04` requirement that per-memory access telemetry must exist before claiming high-salience memories are unused.

## Risks

- **Coach-back becomes noise.** If the threshold is tuned too high, every write gets lectured and agents ignore the receipts. Start permissive, measure the coach-back rate in Phase 195, and tune down.
- **Auto-promotion admits something wrong.** This is the highest-stakes change in v8.30 — gold is what agents rely on directly. Mitigations: min-age before eligibility, conflicts always route to humans, gold stays revocable, and hash-chained receipts make every admission auditable. Consider shadow-mode first (compute the decision, log it, promote nothing) for one cadence.
- **Routing the mem0-direct tools breaks existing agents.** Their response shapes must stay compatible. Add contract tests against the current shapes before changing the handlers.
- **Salience migration touches a hot table.** Coordinate with Phase 188; keep the migration additive.
