## Objective

Make MemRoOS the shared control plane for the Mark Kashef-style agent stack by giving every agent/interface the same compact truth packet and the same durable run ledger.

This is the first v8.3 slice. Do not start by replacing Hermes, building a mobile app, drawing a graph UI, or launching a swarm. Build the substrate that makes all of those replaceable.

## Scope

- Define a typed `AgentContextPacket` contract.
- Add an endpoint/tool/CLI debug path that returns the packet for a goal or active task.
- Reuse existing context/proof substrates where possible:
  - Phase 107 Agent Context Bus
  - Phase 103 checkpoint/resume/handoff
  - Phase 104 memory traces
  - Phase 117 efficiency events
  - Phase 120/121 provenance/audit chain
  - existing hive/action/delegation records
- Define a canonical run-ledger read model over tasks, events, artifacts, approvals, costs, verifications, and handoffs.
- Add receipts for context packet assembly: included, denied, skipped, stale, below-threshold.
- Add deterministic tests for packet content and ledger reads.

## Non-Goals

- No Hermes replacement.
- No full mobile app.
- No graph-first UI.
- No autonomous agent swarm.
- No new memory backend.
- No new policy engine beyond calling existing gates/receipts where available.
- No raw sensitive payloads inside context-packet receipts or ledger proof receipts.
- No attempt to solve all v8.1/v8.2 enterprise tenancy/policy work in this phase.

## Context Packet Contract

The packet should be compact enough to fit in an agent prompt, but complete enough to prevent restating background.

Required fields:

```ts
type AgentContextPacket = {
  packetId: string;
  generatedAt: string;
  actor: {
    agentId: string;
    userId?: string;
    delegatedChain?: string[];
  };
  goal: {
    id: string;
    title: string;
    status: "planned" | "active" | "blocked" | "complete";
    acceptanceCriteria: string[];
    lane: "research" | "code" | "memory" | "deployment" | "email_doc" | "gtm" | "safety" | "ops";
  };
  scope: {
    project?: string;
    repo?: string;
    client?: string;
    cwd?: string;
  };
  constraints: {
    requiredVerification: string[];
    forbiddenActions: string[];
    approvalRequired: string[];
    policyNotes: string[];
  };
  memories: Array<{
    id: string;
    title?: string;
    beliefStage: "bronze_raw_source" | "silver_candidate_claim" | "gold_operational_truth";
    provenance: string[];
    authorization: "allowed" | "redacted" | "denied";
    whyIncluded: string;
    caveat?: string;
  }>;
  decisions: Array<{
    id: string;
    summary: string;
    source: string;
  }>;
  recentRunState: {
    latestEvents: string[];
    pendingApprovals: string[];
    latestProofReceipts: string[];
    handoff?: string;
  };
  receipts: Array<{
    source: string;
    status: "included" | "denied" | "skipped" | "stale" | "below_threshold";
    reason: string;
    pointer?: string;
  }>;
};
```

## Run Ledger Contract

Phase 132 does not need to migrate all storage into one new table. A read model is acceptable if it exposes one consistent contract over existing sources.

Required surfaces:

- task rows: goal id, lane, owner, status, acceptance criteria, created/updated timestamps
- event rows: actor, action type, summary, source, timestamp
- artifact rows: path/url/id, kind, source, hash when available
- approval rows: requested, approved, denied, bypassed, reason
- cost rows: model/provider, route reason, estimate/actual when available
- verification rows: lane, required proof, proof status, command/source receipt
- handoff rows: resume marker, last known blocker, next action

## Skill Boundary Decision

Phase 132 should not create new skills yet, but it must preserve the boundary for Phase 134:

- **Core product**: context packet schema, context endpoint, ledger read model, proof receipts, policy decisions, audit chain.
- **Portable skills later**: "how an agent consumes the context packet", "how an agent runs shipcheck", "how to edit GSD roadmap safely", "how to conduct bounded discuss/review council".

## Implementation Steps

1. Locate existing context/proof data sources and document which fields can feed the packet today.
2. Add the `AgentContextPacket` type and builder in the narrowest shared server-side module.
3. Add a read route/tool for `GET /api/agent-context?goal_id=...` or the existing MCP-equivalent seam if better.
4. Add a CLI/debug command for local inspection.
5. Add a run-ledger read model that federates existing hive/checkpoint/evidence/provenance sources before introducing new tables.
6. Add deterministic fixtures:
   - known goal with gold memory and prior handoff
   - denied memory should produce receipt but not raw content
   - skipped/stale source should be visible as a receipt
   - verification requirement should appear in constraints
7. Add docs for packet size budget and receipt privacy.

## Verification

- Route/tool smoke test for a fixture goal.
- Security test proving denied/redacted memory does not leak raw content.
- Typecheck.
- Build.
- If runtime code is edited, run the existing route/auth/contract gates relevant to touched surfaces.

## Acceptance Criteria

- A fresh agent can call the packet route/tool for one fixture goal and receive all required fields without reading chat history.
- A denied/private source appears as a receipt, not as content.
- A known prior handoff and required verification surface appear in the packet.
- The run-ledger read model returns latest events, proof receipts, and handoff rows for the same goal.
- The implementation does not require Hermes, Discord, Telegram, Codex, or Claude-specific state.
