# Phase 178 Plan 01 — Paperclip / MemroOS Two-Seam Memory Integration (Option D)

**Phase:** 178
**Milestone:** v8.22
**Requirements:** MEMCLIP-01, MEMCLIP-02, MEMCLIP-03, MEMCLIP-04, MEMCLIP-05
**Depends on:** Phase 146 (FLEET-17..21 contract), `paperclip/doc/plans/2026-03-17-memory-service-surface-api.md`, current Paperclip tool-gateway work
**Source opinion:** [`docs/integrations/paperclip-option-d-2026-07-21.md`](../../../docs/integrations/paperclip-option-d-2026-07-21.md) — Opus 4.8 architectural opinion, 2026-07-21.
**Status:** potential plan

## Goal

Land Option D end to end. MemroOS integrates at exactly two Paperclip *core*
seams — the planned `MemoryAdapter` plugin for push and the existing
`toolConnections` MCP gateway for pull — and zero Paperclip adapters gain a
single line of MemroOS-aware code. Paperclip becomes one customer of MemroOS;
the standalone-MCP-server pitch (currently demonstrated at
`~/.cursor/projects/mcps/memroos`) is preserved.

## Tasks

### Task 1 — MEMCLIP-01: Write the Memory Path (FLEET-2x) §4 clause

Append a new `§4 "Memory Path (FLEET-2x)"` section to
`docs/integrations/paperclip.md` (the Phase 146 contract). Three required
subsections:

1. **§4.1 Policy split.** Two-tier authorization:
   - **Binding access** — Paperclip owns (which agent may call which
     provider at all). Resolved at `paperclip/server/src/services/heartbeat.ts`
     via the existing tool-gateway machinery.
   - **Record content** — MemroOS owns (permission-aware pack assembly,
     redaction, retention). MemroOS's authorization wins on what is in the
     bundle.

2. **§4.2 Gateway token invariants.** Every MemroOS write originating from
   a Paperclip-issued gateway token MUST:
   - Resolve that token to `{companyId, agentId, runId}` (see §4.3 below
     for the introspection requirement).
   - Be idempotent on `(run_id, content_hash)`. The same content written
     twice from the same run collapses to one MemroOS record and produces
     two linked `memory_operations` rows on the Paperclip side.

3. **§4.3 No shared database, no federation.** Restate the Phase 146
   boundary rule. MemroOS does not read Paperclip's tables; Paperclip does
   not write MemroOS's tables. The MCP server and the `MemoryAdapter`
   plugin are the only contracts. (No code change; this restates §3 of
   the existing contract.)

**Files:** `docs/integrations/paperclip.md` only. The clause is a contract
amendment, not a runtime change.

**Verification:** `grep -n '§4\|FLEET-2x\|Memory Path' docs/integrations/paperclip.md`
returns the new section.

### Task 2 — MEMCLIP-02: MemroOS `MemoryAdapter` plugin with two paths

Implement MemroOS as the **Phase 1 hosted memory adapter** for Paperclip per
the 2026-03-17 plan. Two paths, one plugin:

#### Push path — `pre_run_hydrate`

Paperclip's `pre_run_hydrate` hook (planned in
`paperclip/doc/plans/2026-03-17-memory-service-surface-api.md`) calls
`MemoryAdapter.preRunHydrate(ctx) -> MemoryContextBundle`. MemroOS's
implementation:

1. Reads the binding context from `ctx` (`companyId`, `agentId`, `runId`,
   `issueId`, optional `projectId`).
2. Calls MemroOS's existing permission-aware pack assembly
   (`apps/memroos/src/lib/memory/pack.ts` — same code path used by the
   standalone MCP server today).
3. Returns a `MemoryContextBundle` whose primary rendering is plain text
   (so the universal `instructionsFilePath` seam can carry it as a file).

#### Pull path — `toolConnections` row

Register MemroOS as one Paperclip `toolConnections` row of transport
`remote_http`. Paperclip core's existing `buildPaperclipRuntimeMcpServers`
(`paperclip/server/src/services/heartbeat.ts:2135`) mints a per-run gateway
token and hands the MCP server set to every adapter via
`AdapterExecutionContext.runtimeMcp`. Adapters that wire `runtimeMcp`
(claude-local, codex-local today) get MemroOS natively.

**Files (new):**

- `apps/memroos/src/integrations/paperclip/memory-adapter.ts` —
  `MemoryAdapter` implementation. Exports `preRunHydrate`, `postRunCapture`,
  `onIssueComment`, `onIssueDocument` (the four hooks from the 2026-03-17
  plan §3).
- `apps/memroos/src/integrations/paperclip/instruction-file-renderer.ts` —
  renders a `MemoryContextBundle` as a markdown instructions file that
  `--append-system-prompt-file` can consume (universal CLI/cloud seam) and
  that gateway envelopes can carry.
- `apps/memroos/src/integrations/paperclip/README.md` — how to register
  the adapter against a Paperclip instance (env vars, the
  `toolConnections` row insert).

**No changes** under `paperclip/packages/adapters/*/src/**`. Verified at
the end by grep gate (Task 5).

### Task 3 — MEMCLIP-03: Paperclip tool-gateway token introspection

The `toolMcpGatewayTokens.subjectId` field already exists at
`paperclip/server/src/services/heartbeat.ts:~2129`. Make it readable by
the callee (MemroOS's MCP server) without weakening the token's
confidentiality. Two changes in Paperclip core:

1. Add a `subject_lookup` route to the tool gateway, mounted alongside the
   existing token-issuance route. It accepts a token (passed by the
   MemroOS MCP server on the first call) and returns the resolved
   `{companyId, agentId, runId, expiresAt}` — the same fields already
   present in `toolMcpGatewayTokens`.
2. Document the route in `paperclip/doc/SPEC-implementation.md` (or the
   tool-gateway spec doc if there is one) so future adapter authors
   understand the contract.

MemroOS side: the MCP server's first call per run resolves the token via
this route and caches the resolution in-memory for the run lifetime.

**Files (Paperclip repo, separate PR):**

- `paperclip/server/src/services/heartbeat.ts` — new `subject_lookup`
  route in the tool gateway section.
- `paperclip/doc/SPEC-implementation.md` — one paragraph documenting the
  introspection contract.

**Files (MemroOS repo):**

- `apps/memroos/src/integrations/paperclip/token-resolver.ts` — calls the
  `subject_lookup` route and caches the result.

This task is **out of scope** for the v8.22 closeout gate if the Paperclip
PR is not merged in time; the contract clause (Task 1) is enough to lock
the rule, and the introspection can ship in a follow-up v8.23 phase.

### Task 4 — MEMCLIP-04: Split-brain integration test

An integration test asserting the sharpest risk scenario: one run that
both hydrates via the `pre_run_hydrate` hook AND calls `memory.note`
over MCP yields **exactly one** MemroOS record and **two linked**
`memory_operations` rows on the Paperclip side.

**Test scaffold:** place this test next to Paperclip's existing
`packages/adapter-utils/src/mcp-isolation.integration.test.ts`, which
already stands up the gateway harness via
`test-support/mcp-isolation-harness.ts`. Reuse the harness; do not
introduce a new fixture framework.

**Test outline:**

```
// New file: paperclip/packages/adapter-utils/src/memroos-split-brain.integration.test.ts

1. Spin up the MCP gateway harness (test-support/mcp-isolation-harness.ts).
2. Register a mock MemroOS `toolConnections` row that responds to
   `memory.note` and tracks every call.
3. Drive a synthetic heartbeat that:
   a. Calls `MemoryAdapter.preRunHydrate` — assert one MemroOS record
      with `source = pre_run_hydrate` lands in the test sink.
   b. Issues a `toolConnections` gateway token, calls the MemroOS MCP
      `memory.note` with a fixed content_hash — assert:
      - Same MemroOS record (idempotent on (run_id, content_hash)).
      - Two `memory_operations` rows: one for the hydrate, one for the
        MCP call, both with the same `content_hash` and linked via
        `memory_bundle_id`.
4. Repeat the MCP call with the same content_hash — assert still one
   MemroOS record, now three linked `memory_operations` rows.
5. Repeat with a different content_hash — assert two MemroOS records
   (different content), each with its own `memory_bundle_id` and one
   `memory_operations` row from the MCP path.
```

**Files (Paperclip repo):**

- `paperclip/packages/adapter-utils/src/memroos-split-brain.integration.test.ts` (new)
- `paperclip/packages/adapter-utils/src/test-support/memroos-mock-server.ts` (new) — minimal MCP server stub for the test

**Files (MemroOS repo):**

- `apps/memroos/src/integrations/paperclip/__tests__/idempotency.test.ts` —
  unit-level mirror of the integration test, runs in CI without Paperclip.
  Asserts the idempotency rule server-side.
