# Phase 176 — Linear + Circleback Unified Memory Ingestion

**Milestone:** v8.20 Connected Work Memory
**Created:** 2026-07-21
**Status:** planned — highest priority
**Requirements:** CONNMEM-01 through CONNMEM-10

## Goal

Give MemRoOS permission-aware, continuously refreshed recall over all selected Linear workspace information and all accessible Circleback meetings and provider-owned memories. Preserve source identity, links, update/delete semantics, access boundaries, and source-to-index evidence so an agent can answer questions without opening either product while never seeing data the operator is not entitled to access.

“Everything” means every object exposed by the authorized provider APIs/CLI and allowed by an explicit workspace/source policy. It does not mean bypassing provider permissions, ingesting inaccessible workspaces, or silently retaining deleted/revoked data.

## Priority

This phase executes before Phase 177 local-install hardening. It is a product capability and memory-access dependency; installer cleanup remains important but must not delay connected work memory.

## Provider coverage research

The evidence review is maintained in `PROVIDER-COVERAGE-RESEARCH.md` beside this plan.

- **Linear:** a company-wide mirror is technically plausible across every separately authorized organization/workspace. The current GraphQL schema must be introspected at implementation time; every connection must be paginated; archived records require explicit inclusion; organization webhooks cover documented object families but `allPublicTeams` must not be mistaken for private-team access.
- **Circleback:** meeting details/transcripts visible to the authenticated CLI identity are supported by the existing connector contract. A tenant-wide admin identity, separate memories/insights endpoint, webhook/deletion feed, and visibility into every employee’s meetings remain unproven. Those are release gates, not assumptions.
- MemRoOS may say **“entire company indexed”** only when provider totals reconcile across an approved inventory of every company Linear workspace and every Circleback team/user source, with inaccessible and unsupported families reported explicitly.

## Current baseline

- Circleback already has a public CLI-backed meeting/transcript transformer in `scripts/meet-sync/providers/circleback_ingest.py`.
- Existing output is stable Markdown keyed by meeting ID and includes notes, action items, attendees, metadata, and transcripts when returned.
- Existing meeting sync, preflight, QMD collections, `memory_recall`, and six-state source-to-index evidence provide a reusable foundation.
- Historical full ingestion, explicit Circleback “memory” objects beyond fields returned with meetings, change/delete reconciliation, and production operator proof are not yet complete.
- No first-class Linear connector exists in the repository.

## Architecture decision

Use one normalized ingestion envelope and two provider adapters:

1. **Raw provider receipt** — encrypted/private checkpoint containing provider object ID, object type, version/update timestamp, workspace/source identity, permission scope, fetch time, and content hash. Never log tokens or full private payloads.
2. **Canonical source document** — deterministic Markdown/JSON projection with stable ID, source URL, provenance, timestamps, ownership/sensitivity labels, relationships, and searchable body.
3. **Memory projections** — QMD/literal retrieval for complete source fidelity, mem0 for compact durable facts/preferences/decisions, and graph edges for issue/project/team/person/meeting relationships. Raw transcripts and issue histories are not blindly promoted into long-term fact memory.
4. **Sync ledger** — per-provider cursor, object hash, last-seen timestamp, tombstone state, retry/dead-letter record, and source-to-index/recall status.
5. **Unified recall** — query both provider collections through the normal memory facade, returning source links, object types, timestamps, and authorization/provenance metadata.

## Scope

### Circleback

Ingest every authorized historical and new meeting, including all fields exposed by the installed Circleback interface: meeting metadata, attendees, notes, summaries, action items, transcript segments, recordings/share links, and provider memory/insight objects if the interface exposes a distinct memory endpoint. During implementation, run capability discovery first; unsupported object families must be reported as `provider_capability_absent`, not silently claimed as complete.

### Linear

Ingest all authorized selected-workspace objects exposed by the supported Linear API: organizations/workspaces, teams, users referenced by work items, projects, project updates/milestones, initiatives when available, issues and sub-issues, descriptions, comments, labels, statuses, cycles, relations, attachments/links metadata, documents, and relevant history/activity exposed by the API. Binary attachment contents require a separately approved fetch policy; metadata and source URLs are in scope by default.

## Requirements and tasks

### CONNMEM-01 — Provider authorization, company boundary, and least privilege

- Implement explicit Circleback and Linear preflight checks.
- Support provider-recommended OAuth where available; allow API keys only through secret stores/environment files outside the repo.
- Record granted scopes and workspace identities without recording credentials.
- Fail closed on missing scopes, revoked access, workspace mismatch, ambiguous tenant selection, or GraphQL partial-success responses containing `errors`.
- Add allow/deny configuration for every Linear organization/workspace/team/project and Circleback team/account/user source/date range that defines the approved company boundary.
- Require a company-managed identity where supported. For Linear, authorize every company workspace separately and enumerate authorized private teams rather than assuming organization-wide public-team webhooks include them. For Circleback, require proof of a tenant-wide identity or explicitly configure one authorized connector per user/source with consent and stable-ID deduplication.
- Generate a capability manifest from Linear schema introspection and installed Circleback CLI/API discovery before backfill; represent unsupported object families as `provider_capability_absent` and inaccessible families as `authorization_blocked`.

### CONNMEM-02 — Canonical source envelope and schema

- Define stable fields: `source`, `workspace_id`, `object_type`, `source_id`, `source_url`, `created_at`, `updated_at`, `deleted_at`, `content_hash`, `parent_ids`, `participants`, `owners`, `visibility`, `sensitivity`, `captured_at`, and `schema_version`.
- Define deterministic filenames/keys so updates replace the same object and never create `-2` duplicates.
- Keep source text separate from derived memory claims.
- Version transformations and support replay from raw receipts without calling the provider again.

### CONNMEM-03 — Complete Circleback backfill and incremental sync

- Extend the existing connector only after capability discovery against the installed CLI/API.
- Backfill from the earliest accessible date with resumable pagination and bounded batches across every approved Circleback team/account/user source.
- Capture meeting details, transcripts, summaries/notes, attendees, action items, recording/share links, screen-share-derived context when exportable, and provider memory/insight records where supported.
- Establish whether Circleback offers an organization/admin inventory, distinct memories endpoint, webhook/change feed, deletion feed, and account export. If not, document the gap, use provider-supported exports or per-user authorizations where approved, and do not claim tenant completeness.
- Detect updates by provider timestamp/content hash; reconcile removed meetings, revoked access, and per-user overlap using tombstones and stable meeting-ID deduplication.
- Preserve stable meeting IDs and existing `meet-recordings-circleback` compatibility.

### CONNMEM-04 — Linear full-company adapter

- Build a first-class Linear provider module with a typed client boundary, schema-introspection compatibility check, independent connection pagination, retries/backoff, rate-limit/complexity handling, and resumable cursors.
- Backfill every separately authorized company organization/workspace and all in-scope object families, including archived resources with explicit `includeArchived: true` where supported.
- Materialize one canonical record per source object and relationship edges between issues, projects, initiatives, project/initiative updates, teams, cycles, users, documents, comments/reactions, labels/statuses, customers/customer requests, attachments/link metadata, SLAs, dependencies, and parent/sub-issues when exposed and authorized by the current schema.
- Preserve Markdown, source links, status, priority, assignee, creator, dates, estimates, and comments without flattening away identity or chronology.
- Treat HTTP 200 GraphQL responses containing field errors as partial failures requiring retry/accounting, never as complete inventory success.

### CONNMEM-05 — Incremental updates, webhooks, and reconciliation

- Prefer signed Linear webhooks for low-latency create/update/remove events, backed by scheduled reconciliation so missed events self-heal.
- Use polling/cursors for Circleback unless a verified webhook interface is available.
- Verify webhook signatures before parsing or writing.
- Make delivery idempotent and replay-safe; quarantine poison payloads with redacted diagnostics.
- Run periodic full inventory reconciliation to discover deletions, permission loss, and cursor gaps.

### CONNMEM-06 — Memory indexing and claim promotion

- Register dedicated collections such as `linear-workspace` and the existing `meet-recordings-circleback` in source configuration.
- Index canonical documents into QMD/literal retrieval and create graph relationships.
- Extract only bounded, attributable durable claims into mem0: decisions, commitments, stable preferences, action ownership, deadlines, project state, risks, and accepted facts.
- Every derived claim must retain source object ID/URL, quote/span or field evidence, extraction version, observed timestamp, and supersession state.
- Prevent stale issue state or superseded meeting conclusions from outranking current provider truth.

### CONNMEM-07 — Unified recall and cross-source linking

- Extend `memory_recall` or its successor to search Circleback and Linear collections without callers knowing collection names.
- Return lane/source/object type, current status, timestamps, provenance, and deep link.
- Link Circleback meetings to Linear issues/projects using explicit URLs/IDs first and conservative entity matching second.
- Keep uncertain links as reviewable proposals; never silently merge unrelated entities.
- Support questions such as “what did we decide about LIN-123?”, “which meeting changed this project deadline?”, and “what open commitments came from last week’s calls?”

### CONNMEM-08 — Authorization, privacy, retention, and deletion

- Enforce tenant/workspace/team visibility at ingest and retrieval; provider access must not be broadened by MemRoOS indexing.
- Classify transcript and comment content before durable claim promotion.
- Implement provider deletion, workspace disconnect, user deletion/DSAR, retention expiry, and legal-hold behavior across raw receipts, source docs, indexes, graph edges, and mem0 projections.
- Redact credentials, private attachment URLs, and sensitive fields from logs/evidence.
- Provide a dry-run purge report and auditable deletion receipts.

### CONNMEM-09 — Operator controls and observability

- Add connector status showing identity, allowed scope, last successful cursor, lag, object counts by type, indexed/failed/deleted counts, webhook health, and oldest retry.
- Extend the bounded source-status evidence chain to Linear and Circleback object families.
- Alert on successful-empty syncs, count regressions, stalled cursors, auth revocation, webhook signature failures, and indexed-unrecalled content.
- Provide re-sync by provider/object/date range and replay from raw receipts.

### CONNMEM-10 — Tests, backfill proof, and release gate

- Unit tests: pagination, normalization, stable IDs, hashes, Markdown preservation, relationship mapping, claim provenance, delete/tombstone behavior, and scope filters.
- Contract tests: recorded sanitized provider fixtures for every supported object family; no live credentials in CI.
- Integration tests: backfill + incremental update + duplicate webhook + missed-webhook reconciliation + permission revocation + deletion propagation.
- Recall tests: exact issue ID, project name, participant, decision, action item, date, and cross-source meeting↔Linear queries.
- Production proof: reconcile provider totals against indexed totals by object type; manually sample historical and recent records; demonstrate source→index→recall evidence for at least one Circleback meeting and one Linear project/issue/comment chain.
- Run lint, typecheck, fast tests, slow tests, build, security review, and adversarial reviewer before completion.

## Delivery sequence

1. Discovery and data contract: enumerate actual provider capabilities/scopes and approve source/retention policy.
2. Shared sync ledger/envelope and redacted fixtures.
3. Circleback completeness hardening and historical backfill.
4. Linear backfill adapter.
5. Linear webhooks plus scheduled reconciliation.
6. QMD/mem0/graph projections and unified recall.
7. Operator surfaces, deletion propagation, production backfill, and reconciliation proof.

## Acceptance criteria

1. Every approved company Linear organization/workspace and Circleback team/account/user source has an identity/scope receipt and every discovered object family is accounted for as indexed, explicitly filtered, unsupported, deleted, authorization-blocked, or failed—never silently absent.
2. Provider inventory totals reconcile to fetched unique objects, policy-filtered objects, failures/tombstones, and indexed objects by workspace/source and object family. Linear reconciliation explicitly includes archived resources and authorized private teams.
3. Re-running a full sync creates no duplicate canonical objects or duplicate memory claims, including the same Circleback meeting visible through multiple user identities.
4. Provider updates and deletions propagate through all memory projections within the documented SLO.
5. Recall answers cite current source objects and deep links, while superseded claims are visibly marked and rank below current truth.
6. Disconnecting a source or revoking scope stops ingestion immediately and supports verified purge according to policy.
7. Operator counts reconcile with provider inventories and expose gaps by organization, workspace, team/user source, and object family.
8. No credentials or unrestricted private payloads appear in Git, logs, test fixtures, or validation artifacts.
9. “Entire company indexed” remains unavailable in the operator UI/API until the completeness ledger is green across every approved source; successful-empty and unknown-provider-capability states fail closed.

## Non-goals

- Writing back to Linear, editing Circleback meetings, or auto-closing issues.
- Fetching binary attachment contents without a separately approved attachment policy.
- Treating every transcript sentence or issue comment as durable truth.
- Circumventing provider permissions or ingesting workspaces the configured identity cannot access.
- Replacing source systems; MemRoOS remains an indexed memory and recall plane.

## Dependencies and operator gates

- Linear app/OAuth credentials, allowed workspace/team policy, webhook URL reachability, and signing secret.
- Circleback authenticated CLI/API identity and confirmation of any separate “memories” capability.
- Retention/deletion policy and approval for historical backfill volume.
- Production access and destructive purge tests require explicit operator approval.
